## 1. Python mirror (design §14 layer 3)

The goal's M5 asks for a pytest mirror of the CRUD and fidelity scenarios.
Both modules are `unittest` test cases (pytest runs them too) and run in
`crates/pyo3-litchi/tests/run_tests.sh`.

**`test_crud_mirror.py`** reads `results/0289/crud-checklist.tsv` and
replays every cell the Rust checklist records as `ok` through `litchi_py`,
for all 21 formats, iWork included:

| verb | cells | verb | cells |
|---|---|---|---|
| get / find / view | 241 each | add | 80 |
| query | 215 | remove | 115 |
| set / edit / batch | 130 each | move / swap | 68 / 64 |
| create | 20 formats | save | 21 formats |

- Every write is published with `to_bytes` and reopened, as in Rust. An
  `add` must also return the path Rust recorded.
- Fixtures are rebuilt the way `run_format` builds them: test-data files,
  `create()`, the seeds (a copy of `SEEDS`), and `<base> + add <element>`
  chains replayed from that element's add cell.
- The two known failures (`pptx ole remove`, `keynote slide remove`) must
  still fail with a `LitchiError`; Keynote's `create` must still be refused.
- The Python capability report must agree with every `supported` claim of
  the TSV (0 mismatches).
- So that the TSV can be replayed, the checklist now records the
  properties of each successful `set` and `add` as a JSON object (data URIs
  shown as `<PNG>`) and never shortens successful evidence (commit 1).

**`test_fidelity_mirror.py`** replays a sample of `results/0289/fidelity.tsv`:
- the four smallest `exact` files per format (75 files, 19 formats): open
  → empty `File.edit` → `save_as` must return the input bytes;
- all 7 signed files (open → `save_as`), the 14 locked files (open
  reports `locked`) and the one typed refusal (same error code).

**Result:** no mismatch between Rust and Python, so no binding bug was
found. The two modules take about 7.3 s in a debug build; the whole
`run_tests.sh` suite (278 tests) about 39 s.

### 2.4 Finding: an ODT-family paragraph `text` set removes inline frames

The fidelity revert of `frames.oth` and `frames.odm` shrinks the files by
160 bytes. The cause:
- `set /body/p[1] text=…` replaces the paragraph's whole content, so its
  three inline frames are removed;
- setting the old text back restores the text but not the frames.

The report counts this as value-exact, because it compares only the text
value. `writer-images-frames.odt` behaves the same way: setting the text
of `/body/p[2]` leaves 4 of its 5 frames.

This is not marked as a failure: it may be the intended semantics of a
paragraph text set. Still, losing content without a word goes against the
goal's lossless rule. **Follow-up for the owner or ODT lead:** either keep
non-text inline content when the text is set, or refuse the set with a
typed error that names the content it would remove. DOCX was not checked
here.
