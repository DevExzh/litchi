# 0256 — The `litchi` command line

Date: 2026-10-13. Status: implements record 0248 §6 Phase D step 15 (design
§11, goal "CLI" ergonomics bar, record 0015 D1/D4/Q2 command-channel
decisions). Branch `uo2/p15-cli`, cut from trunk `9e3872880a`.

## 1. What landed

A new package, [`crates/litchi-cli`](../../crates/litchi-cli/Cargo.toml),
builds the `litchi` binary. The command line lives in the library target
`litchi_cli` (one public item, `litchi_cli::main`), so the binary is a
one-line shim and the non-iWork gate's per-package `--lib` roots reach the
tests.

| Verb | `litchi-ops` call |
|---|---|
| `create <file> [--type T] [--force]` | `create`, `File::save_with` with `Overwrite::Refuse` (`Replace` with `--force`) |
| `get <file> [<path>] [--depth N]` | `open`, `File::get`, `Node::view_with` |
| `query <file> <selector> [--limit N] [--depth N]` | `File::query`, `Matches::limit` |
| `view <file> [<mode> \| --mode M]` | `File::view`, `File::view_json` |
| `set <file> <path> --prop k=v...` | `File::apply` (`set` item) |
| `add <file> <parent> --type T [--prop k=v...] [--index/--at N \| --after P \| --before P]` | `File::apply` (`add` item) |
| `remove <file> <path>` | `File::apply` (`remove` item) |
| `move <file> <path> [--to P] [--index N \| --after P \| --before P]` | `File::apply` (`move` item) |
| `swap <file> <path1> <path2>` | `File::apply` (`swap` item) |
| `batch <file> (--input F\|- \| --commands JSON) [--atomic \| --best-effort]` | `batch::from_bytes_with_limits`, `File::batch` |
| `capabilities (<file> \| --format T)` | `File::capabilities`, `Capabilities::of` |

Every write saves in place through `File::save` (the leaf's atomic
sibling-temp replacement), or to `--out` through `File::save_as`. A write
whose `Diagnostics::changed()` is false leaves the file untouched (no
rewrite), so an exact no-op stays an exact no-op on disk.

Decisions:

1. **Command channel for single writes.** `set`/`add`/`remove`/`move`/`swap`
   build one `BatchItem` and call `File::apply`, not the native verbs, so a
   CLI line and the same line inside `batch` get identical admission and text
   semantics (record 0015 D1; OfficeCLI scripts replay against `apply`'s
   OfficeCLI newline rules).
2. **Strict by default.** Unknown keys and invalid values are refused
   (record 0015 D4). OfficeCLI's "apply the rest and warn" exists only as
   `batch --best-effort` (item granularity), never the default; it exits 9
   when any item failed and still saves the successful items. The
   property-granularity variant has no ops API (follow-up F3).
3. **`--json` is the library's JSON.** `get --json` is exactly the
   serialization of `Node::view_with` (streamed through
   `View::serialize_into`, so OfficeCLI's member order is kept and view
   failures stay typed). `query --json` is OfficeCLI's `NodesResult`
   (`{"matches", "results"}`) of those views, hydrated one level as OfficeCLI
   does (record 0010 Q13). `view --json` is `File::view_json`;
   `capabilities --json` is the serialized `Capabilities`. Writes print
   OfficeCLI's batch rendering, `{"results": [...], "summary": {...}}` (§3).
   No `{"success", "data"}` envelope is added (delta D1).
4. **Errors on stderr.** `error[<code>]: <message>` plus `item`, `property`
   and `suggestion` lines; with `--json`, OfficeCLI's `ErrorResult`
   (`{"error", "code", "suggestion"}` plus `item`, `property`). Stdout carries
   only results, so `--json` stdout always parses as the documented shape.
5. **Exit statuses** follow the Python exception families
   (`crates/pyo3-litchi/src/errors.rs`):

   | Status | Codes |
   |---|---|
   | 0 | success |
   | 1 | `internal_error`, `cancelled`, `limit_exceeded`, `output_too_large`, `max_depth_exceeded`, `validation_error`, `merge_not_exact`, `refresh_failed`, later codes |
   | 2 | usage (argument parser) |
   | 3 | `not_found`, `path_not_found`, `zero_matches`, `out_of_range`, `range_target_not_found`, `invalid_path`, `invalid_selector`, `invalid_xpath`, `unsupported_path`, `bare_selector_rejected` |
   | 4 | `invalid_value`, `unsupported_property`, `missing_property`, `duplicate_name`, `invalid_argument`, `missing_argument`, `invalid_json`, `corrupt_batch` |
   | 5 | `unsupported_format`, `unsupported_capability`, `unsupported_element`, `unsupported_type`, `unsupported_command` |
   | 6 | `file_not_found`, `file_locked`, `file_exists`, `file_required`, `io_error` |
   | 7 | `corrupt_file`, `invalid_input` |
   | 8 | `document_protected` |
   | 9 | `--best-effort` batch with at least one failed item |

   A unit test maps every `Code::ALL` entry. OfficeCLI uses 1 for every
   error and 2 for "applied with warnings"; Litchi's 2 is clap's usage status
   and the warn case is 9 (delta D2).
6. **Option names.** OfficeCLI's: `--type`, `--prop`, `--index`, `--after`,
   `--before`, `--to`, `--depth`, `--input`, `--commands`, `--best-effort`,
   `--force`, positional view mode. The plan's `--at` is accepted as a
   visible alias of `--index` (one option, not two behaviours). `--atomic`
   is the explicit spelling of the default.
7. **Create.** The type comes from `--type` or the extension; a path without
   an extension gains the type's, and an existing file is refused
   (`file_exists`) unless `--force`, as OfficeCLI does.

## 2. Argument parser (dependency decision)

No arg parser was a normal dependency anywhere in the workspace. `clap` 4 is
already in the lock graph as the facade's dev-dependency
(`crates/litchi/Cargo.toml` `[dev-dependencies]`), so choosing it adds no new
crate to the supply chain or `deny.toml` review, and it gives derive-checked
grammar (`Cli::command().debug_assert()` test), conflicts, help and usage
errors. Default features (colour, suggestions) are off; only `derive`,
`error-context`, `help`, `std`, `usage` are on. `lexopt`/`pico-args` would be
smaller but are new crates and need hand-written help and conflict checks.
Its cost is inside the `--version` startup figure of §6.

## 3. Batch result rendering

`litchi-ops` has no serializer for `BatchCommit`/`ItemResult` (record 0015
W3 planned one). The CLI renders from public fields only:

- result: `index`, `success`; on success `changed` and, for `add`, the created
  `path` (`Applied::path`); on failure `code`, `error` (message),
  `suggestion`, `property` and the failed input `item` (`BatchItem`'s own
  `Serialize`);
- summary: OfficeCLI's `total`, `executed`, `succeeded`, `failed`,
  `skipped`, plus `changed`, `saved` and, for an atomic failure,
  `atomicRolledBack`. An atomic failure lists only the failed item (earlier
  items ran, are counted as `succeeded`, and were discarded); the file is not
  written.

Moving this rendering into ops so Python and the CLI share it is follow-up F1.

## 5. Tests

`crates/litchi-cli/tests/cli.rs` (13 tests) runs the binary:

- **JSON equality with the Rust views** over one fixture per read adapter
  (docx, xlsx, pptx, xlsb, doc, xls, ppt, rtf): `get --json` at depths 0, 1, 3
  and the default against `serde_json::to_value(node.view_with(..))`;
  `query --json` (and `--limit 1`) against the node views; `view --json` in
  text, annotated, outline and stats against `File::view_json`, and text view
  output against `File::view`; `capabilities --json` per file and per
  `--format` (10 formats) against `Capabilities` serialization; OfficeCLI
  member order of `get --json`.
- **Writes per format that supports each verb**: create (docx, xlsx, pptx,
  xlsb, doc, xls, ppt, rtf; overwrite refusal and `--force`); add (docx,
  xlsx, xlsb, pptx, rtf); set (docx, xlsx, xlsb, xls, pptx, rtf, doc); remove
  (docx, xlsx, xlsb, xls, pptx, ppt, rtf); move and swap (docx, xlsx, xlsb,
  pptx, ppt, rtf); `--index`, `--at`, `--after`; no-op leaves the bytes
  unchanged; `--out` leaves the input unchanged.
- **Batch**: atomic default and `--atomic` (exit 3, file bytes unchanged,
  `atomicRolledBack`), `--best-effort` (exit 9, saved, per-item codes and
  echoed items), `--commands`, `--input -` (stdin), malformed payload (4),
  missing input (2), conflicting modes (2).
- **Exit statuses** 2–8 from real failures (usage, path, property with
  suggestion and property name in JSON, unsupported view/format/creation,
  missing file/existing file, corrupt ZIP, encrypted DOC, signed DOCX edit).
- **OfficeCLI smoke seed** (`tests/officecli_smoke.sh`, run by the test):
  31 lines from `examples/word/run-formatting.sh`,
  `examples/excel/cell-formatting.sh` and `examples/ppt/presentation.sh`,
  each cited `file:line` and kept as written with `officecli` replaced. Three
  lines are recorded deltas with their expected status: `font.eastAsia` and
  `lang` on a paragraph add (4, `unsupported_property`) and a bare
  `add / --type slide` (4, `missing_property` `layout`). Step 17 grows this
  into the corpus harness.

Unit tests: exit mapping over `Code::ALL`, format-name round trip, clap
grammar `debug_assert`.

## 6. Measurements

`crates/litchi-cli/examples/cli_get_cost.rs`; release build (`lto = true`,
`panic = "abort"`), pinned with `taskset -c 31`, 10 rounds of A B C C B A
blocks × 30 iterations = 600 samples per leg; shared host (load average
15–23). Evidence: [`results/0256-cli/get-cost.json`](results/0256-cli/get-cost.json).
Binary: 33,019,024 bytes, SHA-256
`0984a08ba8842a1839fe1cf55f838a9f545e1a6dc4b0942c43a206f4dafb201b` (not
committed; rebuild with the command above).

| Fixture, path | in-process open+get+JSON (median µs) | `litchi get --json` process (median µs) | `litchi --version` (median µs) | process − in-process |
|---|---|---|---|---|
| xls `Simple.xls` `/sheet[1]` | 20.3 | 620.7 | 432.3 | 600 |
| xlsx `SimpleMultiCell.xlsx` `/Sheet1/A1` | 124.4 | 946.6 | 434.6 | 822 |
| pptx `sample.pptx` `/slide[1]` | 287.9 | 1,149.5 | 441.9 | 862 |
| docx `drawing.docx` `/body/p[2]` | 3,491.1 | 4,113.7 | 448.7 | 623 |

Every p90 is within 12% of its median (the in-process legs are the widest). Cross-check with
`hyperfine -N` on the same CPU: `/bin/true` 210 µs, `litchi --version`
458 µs, `litchi get` xlsx 966 µs (system time 472 µs vs 121 µs for
`--version`).

Reading: a CLI invocation costs about 0.43–0.45 ms of process start and
argument parsing (about 0.25 ms above `/bin/true`), plus 0.17–0.42 ms of
cold-process work (page faults and first-touch allocation; the in-process
leg is warm), on top of the library call itself. For a small `get` the
process dominates (xlsx 7.6×, xls 31×); for the 95 KB docx the library work
dominates (1.18×). This is the expected shape of a one-shot CLI; agents with
many calls should use `batch` (one process for many items) or the library.
No performance budget of the goal applies to process start, and nothing here
changes a library path. Not measured: write verbs through the CLI (their cost
is the measured ops write plus the same process overhead and one save).

## 7. Deltas vs OfficeCLI

| # | OfficeCLI | Litchi CLI | Kind |
|---|---|---|---|
| D1 | `--json` wraps output in `{"success", "data", "warnings"}` | the node view / NodesResult / batch rendering itself; errors on stderr | deliberate (goal: `--json` equals the node view) |
| D2 | exit 1 for every error, 2 for applied-with-warnings, 3 resident busy | family statuses 1–8, 9 for best-effort failures | improvement |
| D3 | unknown props applied as raw XML or warned (exit 2) | refused (`unsupported_property`, exit 4) | strict default; F3 |
| D4 | `add / --type slide` picks a layout | `layout` required (`missing_property`) | ops behaviour |
| D5 | resident verbs (`open`, `close`, `save`, `watch`, `mark`, `goto`) | absent | deferred with MCP (design §11) |
| D6 | `raw`, `raw-set`, `add-part`, `validate`, `import`, `merge`, `refresh`, `dump`, `help`, `plugins` | absent | ops APIs missing (record 0015 §2.3; Phase E) |
| D7 | `get --save`, `query --find/--compact/--fields`, `set --find/--replace`, `remove --shift`, `add --from`, `create --locale/--minimal`, `view --start/--end/--max-lines/--cols/--range/--limit` | absent | F4, F6 |

## 8. Follow-ups (missing ops APIs and findings)

- **F1** `litchi-ops`: a `Serialize` rendering of `BatchCommit`/`ItemResult`
  (OfficeCLI batch result, record 0015 W3) for the CLI and Python to share.
- **F2** `litchi-core`: `FileFormat` name/extension parsing. The CLI keeps a
  22-entry table (`src/formats.rs`); `litchi-ops` has a private
  `format_of_extension` in `save.rs`.
- **F3** `litchi-ops`: property-granularity "apply the rest and warn"
  (`unsupported = "warn"` on the command channel, record 0015 Q2/Δ1).
- **F4** `litchi-ops`: public view options (`view::mode::Options` is
  `pub(crate)`: OfficeCLI's `--start`, `--end`, `--max-lines`, `--cols`,
  `--range`).
- **F5** CLI: `--unsign` (`Signed::unsign`) and unlocking (`Locked::unlock`,
  `encryption` feature). Deferred: needs a credential-input decision (no
  password on argv), and the `encryption` edge.
- **F6** ops: `add --from` (copy), find/replace on `set`, `remove --shift`,
  `get --save` (binary extraction): the ops admission refuses or lacks them.
- **F7** Finding: `create` of a blank OOXML file (docx, xlsx, pptx, xlsb)
  publishes mode 0600 while OLE and RTF files get the umask default (0664);
  an in-place replace keeps the existing mode. Leaf atomic-writer behaviour;
  not changed here.
- **F8** Packaging: the release binary is 33 MB unstripped; a `strip` /
  `codegen-units = 1` profile override for `litchi-cli` (as `litchi-py` has)
  is a release decision.
