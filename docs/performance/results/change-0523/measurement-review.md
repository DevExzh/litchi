# 0523 CFB/OLE2 measurement and custody review

This review fixes the fresh attribution scope for the 0523 OLE2/OOXML
baseline. The planned baseline revision is `0e6379307c5174babfc832edc6113a16c8e9233a`;
the parent-owned 0523 plan, source manifest, builds, captures, and analysis
remain authoritative for their own receipts. This agent performed no build,
test, benchmark, profile, or capture. The only source change in this batch is
the bounded `CfbOpen` operation-metrics enabler and its focused harness test in
[`tools/perf-baseline/src/lib.rs`](../../../../tools/perf-baseline/src/lib.rs).
No CFB/XLS production source, source-provider type or API, corpus generator,
case selector, or default matrix was changed.

## Measurement decision

Use the existing `cfb_open` selector for direct `OleFile::open` attribution on
the synthetic CFB shapes, and keep the existing fixed
`xls-comments-opaque-heavy` source rows as the representative FAT-heavy XLS
workload. The two families answer different questions and must remain separate:
`cfb_open` isolates the raw in-memory CFB parser, while the XLS source rows
measure the production CFB-plus-BIFF workbook constructor and selected
consumer operation.

The 0523 plan's native matrix is two serial repeats of 1,000 retained samples
with 20 warmups on CPU 2, ordered `r1 xls`, `r1 cfb`, `r2 cfb`, `r2 xls`. Its
CFB group is `cfb_open` over `tiny`, `many-small`, and `few-large`, all with
incompressible payloads. Its allocation matrix is two serial repeats of 30
samples with three warmups in the allocator binary. Its profile matrix is two
repeats of five calls with no warmups: one
`xls_owned_source_open_one_cell` child and one `cfb_open` child for each of the
three shapes. These are the existing scenarios in
[`change-0523/plan.json`](plan.json); no additional benchmark case is needed.

The retained 0511 protocol and profile review are the comparison record, not a
fresh 0523 result. The 0511 native guard used the same tiny and few-large
incompressible CFB rows, while its source profile used the fixed owned-source
XLS constructor. The prior broad `*run_cfb_open` Callgrind toggle was useful
for discovery but included runner work and cannot be used as operation-local
evidence. See the retained [0511 profile-scope review](../change-0511/profile-scope-review.md),
[0511 CFB source review](../change-0511/cfb-source-review.md), and
[0413 profile catalog](../change-0413/analysis/profile.json).

## Existing corpus bindings

The direct CFB runner builds one `Corpus` with
`build_cfb_corpus(shape, PayloadKind::Incompressible)` for each selected shape;
the binding is visible at
[`lib.rs#L9024`](../../../../tools/perf-baseline/src/lib.rs#L9024) and the
generator at [`lib.rs#L13086`](../../../../tools/perf-baseline/src/lib.rs#L13086).
Every generated stream is named `benchmark_stream_NNNNN.bin`, and the last
stream is the target used by the existing reopen oracle.

| Existing selector | Existing shape and payload | Structural role and retained oracle |
| --- | --- | --- |
| `cfb_open` | `tiny`, incompressible; 3 streams × 512 bytes | MiniFAT-bearing smoke guard. The retained 0413/0511 identity is a 3,584-byte archive with a 512-byte target. |
| `cfb_open` | `many-small`, incompressible; 256 streams × 1,024 bytes | MiniFAT and directory/sibling scaling guard. This is already an existing `CorpusShape`; the 0523 plan adds it to the selected CFB matrix. Its current archive identity is emitted by the parent capture manifest. |
| `cfb_open` | `few-large`, incompressible; 4 streams × 4 MiB | Regular FAT-heavy guard. The retained identity is a 16,912,384-byte archive with a 4,194,304-byte target. |
| `xls_owned_source_open` and its list/one-cell siblings; source-backed and eager XLS rows | Fixed `xls-comments-opaque-heavy` generated by `build_xls_comments_edit_corpus` | Realistic XLS/CFB constructor with 256 generated comments, two ordinary worksheets, the `Workbook` stream, eight incompressible opaque streams of 2 MiB each, and opaque metadata. The retained corpus is 16,995,840 archive bytes and has an 80,946-byte Workbook stream; shape/payload/writer-shape overrides are rejected. |

The tiny row is the explicit MiniFAT guard; the few-large row retains the
historical regular-FAT guard. `many-small` exercises the same MiniFAT and
directory paths at a larger sibling count. The fixed XLS row supplies the
FAT-heavy source-open workload without changing the synthetic CFB matrix.
Corpus construction and its initial `OleFile::open`/list/target checks happen
before the measured loops. The CFB runner therefore measures repeated opens of
already materialized bytes, not fixture generation or filesystem I/O.

The current selector binding intentionally does not make a new raw
`cfb_open`-over-XLS case. The fixed XLS source rows are the existing way to
exercise the production `SharedOleFile`/`SourceBackedWorkbook` path. If a later
investigation needs a raw `OleFile` open over those bytes, it must preserve the
same `Corpus` identity and be an explicitly opt-in dispatch change; it is out
of this baseline batch.

## Constructor and consumer boundaries

The direct CFB runner is
[`run_cfb_open`](../../../../tools/perf-baseline/src/lib.rs#L54585). For each
iteration, `expected_file_size` and the input slice are already available. The
operation-local sequence is:

```text
allocation_metrics::begin()
Instant::now()
OleFile::open(Cursor::new(corpus.archive.as_slice()))
Instant::elapsed()
allocation_region.finish() or explicit unavailable sample
file_size() oracle
black_box(&ole)
record_elapsed()
drop(ole) at the end of the iteration
```

The existing constructor timer starts immediately before `OleFile::open` and
stops immediately after it. The allocation region begins at the same boundary
and closes before the file-size oracle, so oracle allocations are outside the
operation observation. The input bytes, file-size expectation, correctness
oracle, black-box retention, and object drop remain in their existing places.
Warmups are excluded from both `elapsed_ns` and the retained operation
observations. `elapsed_ns` is converted with the existing checked helper, and
`from_in_process_observations_without_sink` publishes all retained vectors in
the same `(elapsed_ns, sample_index)` order as the statistics object.

`OleFile::open` delegates to `open_with_limits`. The constructor's current
order is visible at
[`litchi-cfb/src/file.rs#L539`](../../../../crates/litchi-cfb/src/file.rs#L539)
through [`#L720`](../../../../crates/litchi-cfb/src/file.rs#L720): length and
limit checks, header and shift validation, physical-sector bounds, the
fallible physical-role reservation, `load_fat`, `load_directory`, optional
`load_minifat`, `validate_stream_allocations`, and
`validate_physical_sector_layout`. The accepted FAT batching remains at
[`file.rs#L841`](../../../../crates/litchi-cfb/src/file.rs#L841); this review
does not propose another production optimization. The MiniFAT and validation
walks remain visible descendants and should not be treated as redundant work
from a top-level profile share.

The fixed XLS source rows have distinct boundaries. The source-backed runner
constructs its layout once before the loop, then constructs an
`InstrumentedSource` and its `ReadAt` handle for each iteration before starting
the version fence and operation clock. It times
`SourceBackedWorkbook::from_read_at` and the selected open/list/cell operation.
The owned-source runner constructs/clones its `OwnedSource` and probes its
version before the clock on each iteration, then times the same source-backed
constructor and selected operation. Their implementations are at
[`lib.rs#L26720`](../../../../tools/perf-baseline/src/lib.rs#L26720) and
[`lib.rs#L26974`](../../../../tools/perf-baseline/src/lib.rs#L26974).

The production source-backed call path is
`SourceBackedWorkbook::from_read_at_with_limits` →
`SharedOleFile::open_with_limits` →
`OleFile::open_with_limits(ReadAtCursor)` → XLS global parsing. The CFB source
fences are retained before and after the parser at
[`shared.rs#L479`](../../../../crates/litchi-cfb/src/shared.rs#L479) through
[`shared.rs#L526`](../../../../crates/litchi-cfb/src/shared.rs#L526), and the
XLS constructor boundary is at
[`source.rs#L726`](../../../../crates/litchi-xls/src/workbook/source.rs#L726)
through [`source.rs#L743`](../../../../crates/litchi-xls/src/workbook/source.rs#L743).
Do not compare a raw `cfb_open` latency directly with an XLS source-backed
latency: their source type, BIFF parsing, version fences, and consumer work
are different.

## Exact Callgrind profile boundaries

The 0523 profile driver uses `--collect-atstart=no` with
`--zero-before`/`--dump-after` around the owner selected in the plan. For raw
CFB, retain the plan's exact demangled owner:

```text
litchi_cfb::file::OleFile<R>::open
```

The corresponding command shape is:

```text
taskset -c 2 valgrind --tool=callgrind --collect-atstart=no \
  --toggle-collect='litchi_cfb::file::OleFile<R>::open' \
  --zero-before='litchi_cfb::file::OleFile<R>::open' \
  --dump-after='litchi_cfb::file::OleFile<R>::open' \
  --callgrind-out-file=<cfb-child.callgrind> \
  <normal-binary> --case cfb_open --shape <tiny|many-small|few-large> \
  --payload incompressible --warmup 0 --samples 5 \
  --json <cfb-child.json> --corpus-manifest <cfb-child.catalog.json>
```

This owner is narrower than `*run_cfb_open`: for each matching call it
collects the raw `OleFile::open` body and its inclusive descendants, including
FAT, directory, MiniFAT, stream-allocation, and physical-layout validation. It
does not collect the timer calls, the file-size oracle, `black_box`,
`record_elapsed`, report construction, or the final `OleFile` drop. The owner
does not match `SharedOleFile` or the XLS source wrapper.

The CFB corpus generator itself performs one validation `OleFile::open` while
constructing the fixture. Because that call has the same owner and is reached
with collection disabled at process start, it produces a separate setup dump.
The driver must retain that numbered setup dump for custody and use only the
five positive incoming dumps from the benchmark loop for operation attribution.
Setup work surrounding that validation open remains outside the profile. The
setup dump must never be folded into the five-call constructor total.

The old 0413 catalogs also show a fully monomorphized spelling such as
`<litchi_cfb::file::OleFile<core::io::cursor::Cursor<&[u8]>>>::open`, while the
0511 release report prints `litchi_cfb::file::OleFile<R>::open`. The parent
driver's frozen owner must be accepted only when each five-call child receipt
contains it with a positive inclusive instruction count and the dumped tree
contains the expected constructor descendants. If the release build does not
match the frozen owner, retain an explicit unmatched/unsupported result; do
not silently change the frozen owner or fall back to the broad runner toggle.
Any alternate spelling requires an explicitly recorded supplemental protocol.
A zero or unmatched dump is not evidence of zero constructor work.

For the fixed XLS profile child, retain the existing exact owner from the plan:

```text
litchi_xls::workbook::source::SourceBackedWorkbook::from_read_at_with_limits
```

That toggle attributes the complete production source-backed constructor,
including nested `SharedOleFile`/`ReadAtCursor` CFB parsing and XLS globals
parsing. It is a constructor attribution for the fixed XLS workload; it is
not a direct raw-CFB comparison. The selected one-cell operation remains in
the elapsed timer but outside this Callgrind owner, so profile and latency
claims must keep those scopes distinct.

The profile lane is diagnostic attribution. It does not establish a native
latency, allocation, RSS, or speedup claim. The plan's separate native and
whole-child hardware lanes retain those scopes and their limitations.

## Missing metrics and smallest enabler

Before this batch, `run_cfb_open` returned `result(..., None)` after recording
only elapsed statistics and a file-size oracle. It emitted no
`operation_metrics` envelope, so a CFB open had no operation-aligned
allocation status, allocation calls, allocated/deallocated bytes, reallocation
counts, live-byte snapshots, or region peak. It also had no process metrics or
logical source counters.

The smallest correct enabler is the additive bracket now in
[`run_cfb_open`](../../../../tools/perf-baseline/src/lib.rs#L54585):

1. Begin the existing allocation region immediately before the unchanged
   constructor timer.
2. Finish it immediately after the unchanged constructor timer and before the
   unchanged file-size oracle.
3. Convert a disabled region's `None` result into
   `allocation_metrics::unavailable_sample()`.
4. Add one `InProcessObservation` for each retained sample and pass those
   observations to the existing
   `from_in_process_observations_without_sink` helper.

The normal binary has no global allocator wrapper. Its report now carries an
explicit allocation object with status `unavailable` and omitted numeric
vectors, which distinguishes uninstrumented measurement from a measured zero.
The allocator binary calls `allocation_metrics::enable`; its same code path
retains the measured `Sample` and publishes checked allocation calls, bytes,
live-byte, and peak vectors. The allocator lane must verify those measured
values from its own capture. No global allocator state is enabled by the
ordinary harness test.

The raw CFB `Cursor<&[u8]>` path has no logical `ReadAt` observer. The existing
operation helper therefore leaves source vectors explicitly `not_applicable`
for this in-process no-sink operation; it must not publish fabricated zero
read counts. `CfbSharedOpen` is the existing source-observed alternative: it
uses `InstrumentedSource` and `SharedOleFile`, and therefore has different
source/version and constructor semantics. Adding a `Read`/`Seek` observer to
raw `OleFile::open` would change the reader type and source attribution, so it
is outside the smallest enabler and this frozen baseline.

Process/RSS and PMU counters are similarly unavailable at this operation-local
boundary. `/usr/bin/time` and `perf stat` in the parent driver cover the whole
child, including setup, report work, and drops; they cannot be relabeled as
constructor-local evidence. The operation metrics deliberately leave process
vectors absent from the in-process observations.

## Focused harness proof

The new
`cfb_open_operation_metrics_align_and_report_unavailable_allocator` test in
[`lib.rs`](../../../../tools/perf-baseline/src/lib.rs) runs the existing
`cfb_open` runner with one warmup and three retained samples for both the tiny
MiniFAT and few-large regular-FAT shapes. It checks that:

- the operation sample count is three and its sample indices equal the
  elapsed-statistics sample order;
- the ordinary test binary publishes allocator status `Unavailable` with
  omitted allocation call, byte, and region-peak vectors, while the raw CFB
  source status remains `NotApplicable` without fabricated read counts; and
- a fresh `OleFile` reopen still passes the existing file-size, stream-count,
  and target-payload oracles for both shapes.

The test holds the allocator metrics test lock so it cannot overlap the
allocator-state override tests. It never calls the process-global
`allocation_metrics::enable`; actual measured semantics belong to the parent
allocator binary captures. No test or capture was run in this review. Root
should run the serial 0523 build, focused harness test, full required CFB/XLS
validation, native/allocation captures, and exact-owner profile receipts after
freezing this source.

## Custody limits and deferred work

The synthetic CFB rows use deterministic in-memory writer output. They expose
FAT/MiniFAT and directory scaling, but do not represent cold filesystem I/O,
physical source latency, or all native Office producer layouts. The fixed XLS
corpus is also generated by the harness, although its Workbook and opaque
streams exercise the production source-backed path. Keep fixture generation,
setup, query, correctness oracles, report construction, and object drops out
of constructor attribution as described above.

This baseline admits no optimization and makes no before/after speedup claim.
The retained FAT batching and all CFB validation/error-order behavior remain
the control. Any future candidate must use the operation-local owner and the
same corpus identities, then pass matched native latency, allocation, source,
and adverse-regression review. ODF work remains deferred until the OLE2/OOXML
optimization goal is complete, and iWork is excluded.
