# Next work after the DOCX tail-append baseline

The full non-iWork performance goal remains open. Change 0479 establishes the
current single-copy logical-tail baseline; it does not change production or
supply the required explicit-window append capability.

## First production experiment: share the publication target XML

Publication is the largest measured phase at roughly 160 ms for 131,072
paragraphs, and it retains an additional target XML allocation when passing
bytes to OPC. Test the existing shared-Arc OPC handoff first, preserving source
recapture, fingerprints, full validation, unchanged member passthrough and
inverse retention. The [candidate map](candidate-mechanisms.md) identifies the
exact existing seam and proof obligations. The phase's total CPU share does
not measure the clone's CPU cost; this is primarily a concrete ownership/heap
experiment, and a latency benefit must be demonstrated independently.

Use the frozen 0479 source/binaries/corpus as the control, with authenticated
source restoration or a clean fixed build path if a matched rebuild is needed.
Repeat the same total/phase matrix and retain peak, requested bytes, live
retention, RSS, latency, logical I/O, exact output/inverse identity and all
5% review flags. Keep the candidate only for a practical verified benefit or
a measured necessary enabler. Avoid grouping unrelated parser changes into
this experiment.

## Then reduce the measured scanner subtree

Source-backed scanning accounts for 68.037% of sampled lifecycle periods.
Evaluate reuse/derivation of validated candidate ranges against the complete
current scanner authority and refusal/readback proof. Removing a scan must
preserve event/depth/paragraph bounds, namespace handling, malformed-input
precedence, exact lexical ranges and typed allocation failures. Source
recapture and publication checks remain required.

The source/allocator audit separately identifies per-event local-name clones
and exact-one-element paragraph-vector growth after 4,096 ranges. Borrowing
names within an event and using finite checked index growth are smaller
scanner experiments, but allocator requested-byte totals are not CPU or
physical-copy attribution. Geometric spare capacity can increase retained
heap. Measure these mechanisms separately where the memory tradeoffs differ,
using differential admitted/refused/limited fixtures against the current
parser. None of these improvements to materialized transactions alone closes
the explicit-window requirement below.

## Keep explicit-window append as a separate required workstream

ADR 0005 distinguishes random-access edits from a tail-only streaming API.
The existing snapshot exposes complete XML and paragraph ranges, and its patch
retains complete before/after XML. Reusing that public shape while asserting
constant memory would be misleading. Design the explicit tail capability with
format-owned admission, stable source/version checks, finite input/output/event
limits, caller-provided replayable scratch where needed, sequential publication,
exact untouched compressed-member preservation and a concrete reversible
publication/patch contract consistent with ADR 0003. Draft an ADR only if the
required contract truly conflicts with accepted decisions.

Count total retained owners and caller scratch separately. Validate the whole
source before output when required by the refusal contract, even if that means
replaying an immutable source. The proof must include final body/section
placement, malformed tails, limits, source mutation, cancellation, partial
sink failure and exact inverse restoration. The ordinary current API refuses
`sectPr`; do not silently admit it by weakening the parser. A larger supported
section grammar requires a separately reviewed format capability.

## Remaining coverage

Repeated 64/256 appends require distinct reopen/edit/commit/publication
lifecycles under the present one-operation limit. They remain missing from
this baseline. Keep the checklist's four append meanings separate: fresh
streaming creation, logical existing-structure append, adding a package Part,
and arbitrary edit/repackaging. Native-producer corpora, filesystem/cold and
high-latency range sources, atomic replacement, broader CRUD, cache and worker
scaling, and other non-iWork requirements remain in the program audit.
