## Admission, pinning, and bypass

The selected image has 2,097,152 logical bytes. The pinned presentation root
uses 691 managed bytes; primed metadata uses 6,248 bytes. The exact Memory cap
is therefore 2,097,843 bytes, and the one-under cap is 2,097,842 bytes.

- Exact admission first fails reservation, evicts metadata, and succeeds on
  retry. Managed Memory reaches the exact cap. Dropping the image handle leaves
  its bytes cached until the view is dropped.
- One-under records two reservation failures and one eviction, then returns
  typed `Memory` refusal. The request window performs zero source reads and
  accepts zero output bytes. Only the 691-byte root remains charged.
- With a two-entry cache, A occupies the slot beside the pinned root. Holding
  A while reading B increases bypasses without evicting retained entries, and
  B's caller handle adds one payload reservation. Dropping the handles releases
  B's uncached reservation. Reloading B evicts the now-unpinned cached content
  and retains B without another bypass. A is image 0; B is selected image 3.
- With cache capacity `P - 1` and 128 entries, the image is returned uncached.
  Memory is 2,097,843 while its handle lives and 691 after it drops. A second
  read again loads and bypasses the oversized payload.

The ordinary image request window records 69 calls / 2,097,859 returned source
bytes. The oversized reload records 74 calls / 2,098,581 bytes, including its
metadata lookup. Pinning's A/B window records 143 calls / 4,196,440 bytes; its
B reload records 74 / 2,098,581. These are instrumented logical ReadAt windows,
not physical I/O or copied-byte counts. Non-applicable row windows are null.

Repeated publication keeps the same source view across three exact outputs
while creating a new consumed destination editor each time. The shared
destination OutputBytes ceilings are 94,542 bytes for plain and 100,799,529
for media-rich, exactly three outputs. After the result, plan, and sink have
all been dropped for each publication, destination Memory and Objects are
zero. The fourth publication returns typed
`OutputBytes` refusal and accepts zero bytes in its own sink.

## RSS repeat flags and disposition

All 27 flags above the 5% review threshold are process RSS points. There are
no non-RSS flags. The image lanes' entry RSS already differs between repeats:

| Lane | R1 entry RSS MiB | R2 entry RSS MiB | Change |
| --- | ---: | ---: | ---: |
| Exact admission | 162.949 | 265.027 | +62.644% |
| One-under | 272.000 | 546.715 | +100.998% |
| Pinned eviction | 546.656 | 272.055 | −50.233% |
| Oversized bypass | 546.836 | 316.422 | −42.136% |

Every phase RSS value is constant throughout each of these eight image
processes. Their VmHWM values are also constant and exactly equal the separate
`/usr/bin/time` maximum RSS after converting KiB to bytes. The high-water mark
was already reached at the first retained entry, which follows corpus/gate
setup and warmups. Source inspection confirms each observation freshly reads
`/proc/self/status`; it is not a cached metric or another process's RSS.

The capture does not isolate the cause of the differing entry RSS. It cannot
support comparative RSS retention, release, improvement, or regression claims.
The flags are retained without selecting replacement runs. The managed
reservation and source-read findings remain descriptive and exact. Lifecycle
and repeated-publication entry-RSS changes are within 1.56%; that is not a
causal RSS claim either.

Before making comparative RSS claims, isolate and profile setup/warmup state
in a new predeclared protocol. Continue native-producer and cold/range-source
coverage without treating corpus-gate allocation as a production hotspot.
