## 0649 — the 133.61 ms real-deck shape-text edit is six whole-slide MCE rewrites, and the revision proof is 0.51% of it

Change [0638](0638-facade-and-ordinary-save-selectors.md) measured one `opened_presentation_transaction().set_shape_text(..)` plus `apply_opened_presentation_commit(..)` on the real 108 KB, 103-member `slide-section-test.pptx` at **133.61 ms** — 95.7% of that deck's lifecycle, 490× its complete serialization, 68.7× the same edit on the generated corpus — and said *"Nothing in this record explains it."* It is explained. The edit is four documented public calls, so a retained scratch probe times each one: the **capture (`opened_presentation()`) is 59.900 ms and the commit's recapture 62.928 ms — 95.9% of the 128.123 ms edit** (96.44% of its cycles, 96.08% of its instructions), while the working clone, `set_shape_text` and the publication are the other 4%. Inside a capture, `litchi-pptx` runs **44 markup-compatibility passes over 819,319 bytes — 1.03× the deck's entire uncompressed size, per capture** — and **every one rewrites**: three per slide (`SlidePart::from_part`→`root_name` to learn the root is `p:sld`; `SlidePart::name`→`c_sld_name` to read one attribute of the second element; `notes::load_snapshot`→`root_conformance`→`scan_xml`, on a deck with **no notes slides at all**) plus five over `ppt/presentation.xml`. Change [0588](0588-mce-codec-namespace-emission.md)'s frozen namespace emission then makes each pass produce **16.3× its input**: one edit emits **62,181 start tags carrying 373,086 re-declared namespace bindings — 6.00 per element — and 28,064,911 bytes of markup, 259× the source archive**, all of it thrown away. **The attribution is proved by construction, not by profile share.** A marker-stripped control — the same deck with the MCE namespace URI replaced by an equal-length URI the codec does not recognize, so member count, element count, part-decode count (59), capture count (2), fingerprint bytes (1,568,820) and uncompressed byte total (796,725) are *identical* — costs 7.822 ms: **93.9% of the edit removed** by nothing but which branch of `process_markup_compatibility` each part takes. Natively the MCE codec plus its `memmove` is **80.69%** of the capture's cycles and 79.68% of the edit's. **The complete-package revision proof is not the mechanism**: `sha2::sha256::x86_sha::compress` is **0.51%** of the capture's cycles, about 0.9 ms of 128 — while callgrind, running software SHA-256, puts `package_fingerprint` at 3.24%, a **6.4× overstatement**, and change 0590 measured the same function at 34.94% on a *generated* corpus where every MCE pass borrows. Change 0645's revision-proof design is bounded by that 0.51%. **What makes the generated corpus 68.7× cheaper is measured, not guessed**: 0 of its 61 members mention the MCE namespace against 43 of 103 carrying 93.0% of the real deck's bytes, so all 43 of its capture's passes return `Cow::Borrowed` after the namespace scan — 5.57× fewer bytes on a path 13.9× cheaper per byte (189.8 MB/s against 13.7), and 5.57 × 13.9 = 77 against the capture's measured 77.3×. That is 0587's corpus gap at its sharpest: **every prior PPTX record measured on decks that never reach the code costing 94% of a real deck's edit.** Change [0637](0637-pptx-eager-slide-catalog-memo.md)'s catalog memo was applied to the base and re-counted: **every counter identical**, because the capture builds one borrowed view and makes one query through it. One edit of a 108 KB file allocates **91 MB, 841× the archive**. Four candidates are sized in MCE output bytes and all four frozen: a per-part memo (−62.8%) needs `Copy` off a public view and answers no bounded-resources question; a per-slide recapture delta (−43.5%) and prefix-limited reads (−62.8%) both move when a refusal happens; and the writer fix is 0588's, already withdrawn. `performance_claim: none`; no file under `crates/` changed. OLE2/OOXML remain active; ODF stays deferred; iWork is excluded. [Record and limitations](0649-pptx-opened-transaction-real-deck-edit.md); [retained evidence](results/change-0649/README.md).

## 0649 — clause (d) is violated by a factor of 259 on the one PPTX route a caller edits through, and no prior record could see it

Record: [0649](0649-pptx-opened-transaction-real-deck-edit.md).

`docs/GOAL.md`'s definition of done asks for work proportional to accessed content (clause c) and for unrelated content not to be parsed (clause d). This record evaluates both on the documented PPTX edit route for the first time on a real deck, and both fail by large, measured margins. Clause (c): replacing the text of **one shape on one slide** costs 44 whole-part markup-compatibility rewrites per capture and two captures per edit, so **every slide of the deck is fully decoded six times** to publish a change to one of them; the accessed content is 34,041 bytes of one slide and the parsed content is 1,726,827. Clause (d): the deck carries no notes slides, yet `notes::load_snapshot` decodes all thirteen of them inside every capture to discover that — 273,892 bytes per capture, 33.4% of the capture's markup-compatibility input and 38.95% of its instructions, entirely unrelated to the edit. And the produced-and-discarded intermediate is **28,064,911 bytes for a 108,164-byte archive, 259×**. Three tiers as the audit requires. **Measured**: the phase decomposition (capture 59.900 ms, commit 62.928 ms, 95.9% of a 128.123 ms edit, A/A floor 4.31%); every deterministic count, which is identical across repeats by construction; the native cycle and instruction isolation pairs; and the marker-stripped control removing 93.9%, on a deck proved structurally identical by the count table rather than asserted. **Modelled**: the −62.8% / −43.5% / −62.8% ceilings of the three in-scope candidates, which are counts of removable MCE output bytes on a path the cycle measurements show is linear in exactly that quantity — but a count of removed work is not a saving until the cost it trades into is measured natively, and none of the three is implemented. **Unknown**: how many real decks declare the MCE namespace (this one does in 43 of 103 members carrying 93.0% of its bytes; change 0588 found 61 of 62 `.docx` fixtures declaring it in `word/document.xml`), whether the DOCX and XLSX ordinary-save edits share the shape, and what a Strict-conformance deck costs, where `root_conformance` runs its scan twice per part. The audit's most useful output is a correction to how this program reads its own corpora. Change 0587 recorded a corpus gap; this record measures its size: the harness's generated PPTX corpus takes the **borrowed** branch of `process_markup_compatibility` on every one of its 43 capture passes, the real deck takes the **rewriting** branch on all 44, and the two branches differ by 13.9× per byte. Every PPTX performance number this program has published — 0590's, 0598's, 0607's, 0637's — was taken on the cheap branch. Two further audit facts reported without action: `litchi-perf-baseline-alloc` reports no allocation metrics for change 0638's ordinary-save selector family, because the harness-only change that registered it did not reach `allocation_metrics.rs`; and callgrind overstates this path's SHA-256 by 6.4×, which is the program's own stated hazard reproduced with both numbers side by side for the first time. `performance_claim: none`; no file under `crates/` changed. OLE2/OOXML remain the active priority; ODF stays deferred until completion; iWork is excluded.

## 0649 — no boundary moved, and the ADR 0003 revision binding is priced at 0.51% of the path it was suspected of owning

Record: [0649](0649-pptx-opened-transaction-real-deck-edit.md).

No production code changed, so no ADR boundary moved and no accepted hash changed. Every call the probe makes is a documented public entry point — `litchi_pptx::Package::open`/`from_bytes`/`new`/`presentation_mut`/`to_bytes`/`opened_presentation`/`opened_presentation_transaction`/`apply_opened_presentation_commit`, `Snapshot::edit`/`slides`, `Transaction::set_shape_text`/`commit`, `Commit::is_changed` — and no typed error, limit, refusal point, validation order, output byte or public API is reachable from them. **ADR 0005's mandatory-validation clause is observed, not altered**: every validation inside the measured region still runs in the same order — the slide-reference resolution, the one-to-one identity checks, the relationship-type checks, the per-slide name parse, `notes::load_snapshot`'s ADR 0013 notes-topology gate, the name-index build, `compact_changed_slides`' semantic re-read, and `Patch::capture` — and the record's whole point is that three of those validations each decode every slide in full. **ADR 0003's complete-package revision binding is measured rather than assumed**: `package_fingerprint` runs twice per edit over 1,568,820 bytes, unchanged in count and in input from the base, and is **0.51% of the capture's native cycles and 0.72% of the edit's**. That number matters to two open designs. Change 0590 recorded part (c) — a cheaper revision proof — as designed and unimplemented, and change 0645 is working its format; this record bounds what either can be worth on a real deck at 0.51% of a capture, and explains the discrepancy with 0590's 34.94%: callgrind runs `sha2::sha256::soft::unroll::compress` while the hardware runs SHA-NI, a **6.4× overstatement** here, and 0590's corpus was a generated deck on which every markup-compatibility pass borrows and the fingerprint is the only bulk work left. **ADR 0006's determinism is untouched**: no output byte is produced by this record, and the harness leg's retained samples each reproduced change 0638's frozen publication digest and edit outcome. **The measurement leg is disclosed and bounded.** The deterministic counts come from a patch adding twenty-five `AtomicU64` counters and one `Mutex<Vec<u64>>` trace behind twenty-six `bump`/`trace` calls in seven files of `litchi-ooxml-common` and `litchi-pptx`; it produced no timing, cycle or instruction number, it is retained in the packet, and it was reverted with `git checkout -- crates/` before the gates, which then ran on a tree `git status` reports as identical to the base. The probe's own counting global allocator lives in the probe, never in `tools/perf-baseline`, whose source policy forbids `#[global_allocator]`; change 0519's `allocator-probe` is the precedent. No new `unsafe` anywhere, no new dependency, no hidden global Rayon pool, no ambient I/O: the probe reads one caller-named path and writes nothing but its own control deck. The base predates change 0638, so that record's harness-only diff (commit `15363b3a8`, touching only `tools/`) was applied to build the two harness binaries and reverted; it touches no file under `crates/`, so the crate code measured through it is the base's. **Four designs are frozen, each named with what it moves**: a per-part processed-XML memo would take `Copy` off the public `SlidePart` and `PresentationPart` views — the obstacle change 0637 recorded and declined for `PresentationPart` — and would hold 13.3 MB per capture on a 108 KB file, a bounded-resources question ADR 0005 would want answered in its own record; a per-slide recapture delta moves when a per-slide refusal happens; prefix-limited reads in `root_name`, `c_sld_name` and `root_conformance` move a refusal the other way, since those three sites refuse a malformed tail today only because markup-compatibility validates the complete document first; and the writer-side fix is change 0588's, already implemented, measured and withdrawn because `litchi-docx` parses sliced element ranges standalone and two writers publish the processed stream. The one change that is unambiguously value-identical and in scope is worth 0.29% of a capture's markup-compatibility input, far below the 4.31% floor, and is declined as speculative complexity. `performance_claim: none`. OLE2/OOXML remain active; ODF stays deferred until completion; iWork is excluded.
