# Independent review: change 0475

Review checkpoint: 2026-09-08 UTC. This is a bounded read-only review of the
0475 change note, bundle README, normal/counter replay, CPU attribution JSON,
`analyze.py`, `check.py`, `verify.py`, `seal.py`, and the captured Heaptrack
receipts/exports. No production or benchmark source was changed by this
review.

## Disposition

The normal/counter and CPU evidence is internally consistent, and I found no
material CPU claim that exceeds the captured evidence. The CPU reports keep
`cycles:u` periods as sampled event weights, retain unknown coverage, and
record zero lost, unparsed, and truncated samples. They do not turn periods
into elapsed phase time or add overlapping owner-family rows.

At this checkpoint the bundle is not ready for a final portable/sealed pass:
`heap-attribution.json` and the bundle-level `SHA256SUMS` are absent. The
compression manifests and raw Heaptrack/export receipts exist, but the
Heaptrack attribution result has not yet been produced. Therefore
`verify.py --unsealed` cannot pass its heap-attribution gate, and `verify.py`
with its default sealed mode cannot pass until the result is generated and
the final seal is created. This is a completion gate, not a finding against
the CPU evidence.

## Evidence checks

The CPU JSON values match the retained perf-script exports. P1 has
158,481,691,367 whole-process sampled cycles: 38,009,610,162 (23.983597%) in
the exact `pptx_streaming_create::run` ancestry, 119,137,279,678 (75.174160%)
in materialized preflight, and 1,334,801,527 (0.842243%) unclassified. P2
has 159,062,192,752 total: 38,036,129,108 (23.912740%) writer,
119,764,444,324 (75.294099%) preflight, and 1,261,619,320 (0.793161%)
unclassified. Unknown-frame weight is reported separately (0.410262% and
0.441736%); lost, unparsed, and truncated coverage is zero in both exports.

The whole-process counter context is also preserved accurately: 157,634,913,764
user cycles and 690,745,026,904 user instructions, with the hardware events
scheduled for 83% of the enabled interval. Unsupported LLC load misses remain
unsupported, while the reported zero L1 data-cache misses is not described as
proof that no such misses occurred. These counters include setup, corpus
materialization, preflight, the timed writer, profilers, and teardown.

The change note correctly describes the normal p50 values as unchanged-code
repeatability rather than before/after evidence. It also correctly distinguishes
the exact timed `run` ancestry from `build_corpus`/materialized preflight;
`write_pptx_stream` can appear under both, so a nearest-helper rule alone would
be unsafe. The source audit's `litchi_opc::phys_pkg::PartNameSet` and the
validated Deflate initialization symbols are consistent with the owner-family
names used by the CPU report.

The Heaptrack limitation language is appropriate: the demangled `::run`
filter is empty under Rust v0 symbols, the mangled-token export is supplemental
and uses the same raw traces, and whole-process allocation/RSS values are not
treated as operation-local peaks. No heap conclusion should be promoted until
the analyzer emits `heap-attribution.json`; in particular, the large
preflight reader-construction count must remain separate from timed writer
allocation attribution.

## Final evidence closure

The earlier missing-artifact checkpoint is superseded for attribution: both
`heap-attribution.json` and `owners.json` are now present, and the final live
verification receipt reports status `pass` for all seven lanes, both CPU
profiles, both heap traces, 7,034 source files, and the reused binary. The
earlier live-verification attempt failed only because it used a stale scope
key; that receipt remains retained as an audit trail, while the corrected
`live-verify-final` receipt passes. Capture and export inputs were not changed
by the filter/owner review.

H1 and H2 agree exactly on the selected `writer-under-run` ancestry: 311,120
allocation calls, 6,809,648,242 requested bytes, an 8,875,780-byte projected
event-timeline peak, and zero live bytes/outstanding allocations at exit. The
run ancestry includes observer and report setup. It contains 127 calls and
44,229 requested bytes beyond the 0474 allocator observation, so this peak is
not a timed-operation peak and must not be presented as one.

The exact stack-owner review isolates 16,421 Deflate initialization
allocations of 380,032 bytes each (6,240,505,472 bytes) and 16,421 flate2
output-buffer allocations of 32,768 bytes each (538,083,328 bytes). Together
they account for 6,778,588,800 bytes, or 99.54389065% of run-context requested
bytes, in both heap lanes. This is requested-byte attribution; it is not an
elapsed-time share and does not turn the two independent owner rows or their
peaks into an additive live-memory bound.

One critical interpretation boundary remains: the generic nearest-frame
`ZIP-metadata` category includes some `flate2` buffer frames because generic
type frames can be closer than the owner marker. It must not be used as the
compressor-owner result. `owners.py` uses exact captured stack markers and
disjoint rows for the Deflate initialization and flate2 buffer totals above.
The 33-test parser/filter receipt passed, including exact descriptor matching
and rejection of a malformed selected tail.

Final portable/sealed completion still belongs to the bundle owner: include
this closure in the final seal, remove bytecode, and retain the completed
sealed verification receipt after `SHA256SUMS` is created. No critical CPU or
heap overclaim was found once these scope and owner boundaries are applied.
