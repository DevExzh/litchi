# PPTX streaming transport audit

This is a read-only source audit for the frozen change-0475 PPTX allocation
profiling batch. It records the transport lifecycle and a bounded reuse
candidate; it does not propose or implement a production change.

  `crates/soapberry-zip/Cargo.toml:12-14`; the lockfile resolves `flate2`

## Active PPTX path

`StreamingPresentationWriter<W>` owns a `PhysPkgWriter<BudgetedSink<W>>`
(`crates/litchi-pptx/src/writer/streaming.rs:217-225`). The semantic writer
emits XML fragments directly to the current part. `start_slide` validates the
slide and starts `/ppt/slides/slideN.xml` through `PhysPkgWriter::start_part`
(`streaming.rs:302-365`); `StreamingSlideWriter::finish` closes that part and
then emits and finalizes the slide relationship part (`streaming.rs:489-528`).
There is no deck-sized slide XML buffer in this path.

The PPTX writer's `BudgetedSink` limits bytes accepted by the caller's output
sink (`streaming.rs:635-678`). A partial sink write is retained as accepted
progress, and a zero write becomes `WriteZero`. The output budget includes
ZIP framing and final central-directory output, but is a runtime ceiling rather
than a heap bound (`streaming.rs:867-873`).

`PhysPkgWriter::start_part_inner` prepares and validates the OPC name, reserves
the `PartNameSet`, clones the PackURI, and starts a Deflate ZIP entry
(`crates/litchi-opc/src/phys_pkg.rs:1233-1252`). `PartWriter` owns the active
`StreamingArchiveEntry`; its `finish` only commits the OPC name after the ZIP
entry has finalized (`phys_pkg.rs:1083-1165`).

## Fresh Deflate lifecycle

The Office transport writer owns a low-level `ZipArchiveWriter` and a set of
bounded counters (`crates/soapberry-zip/src/office.rs:5321-5337`). It moves the
archive into one `StreamingArchiveEntry` at a time. `start_entry` performs
name/count/metadata admission, chooses ZIP64 framing from the configured
unknown-size payload ceilings, and calls the low-level owned-entry constructor
(`office.rs:6195-6295`).

At the low level, `ZipArchiveWriter::start_file_owned_with_options` reserves
and appends the normalized member name to `file_names`, reserves one
`FileHeader`, emits the local header, and creates `OwnedCompressedEntry`
(`crates/soapberry-zip/src/writer.rs:1357-1405`). For Deflate it then creates
`DeflateEncoder::new(compressed, Compression::default())` and wraps it in
`ZipDataWriter` with CRC32 enabled (`writer.rs:1406-1426`). The active entry
therefore owns the entire parent archive while the compressor writes.

The write stack has three relevant accounting layers:

1. `StreamingArchiveEntry::write` checks entry and aggregate uncompressed
   limits before forwarding bytes. It increments uncompressed progress only by
   the bytes accepted by the inner entry and captures the first typed failure,
   sink error, limit, and output progress (`office.rs:5346-5450` and
   `office.rs:5550-5645`).
2. `OwnedCompressedEntry::write` checks the compressed ceiling before writing
   generated bytes to the bounded archive sink, then counts only accepted
   compressed bytes (`writer.rs:1821-1870`).
3. `ZipDataWriter` tracks uncompressed size and updates CRC32 from the prefix
   accepted by its inner writer (`writer.rs:1943-2067`).

Finishing consumes the `ZipDataWriter`, finishes the Deflate encoder, writes
the ZIP data descriptor, and appends a `FileHeader` to the archive
(`writer.rs:1881-1924`, `writer.rs:1674-1704`). The descriptor width was chosen
before payload output; `write_data_descriptor` rejects a ZIP32 entry that
reaches the ZIP64 threshold rather than emitting a mismatched descriptor
(`writer.rs:1787-1819`). The streaming entry then reconstructs the parent
writer, updates aggregate counters, and inserts the normalized name only after
successful finalization (`office.rs:5456-5545`).

At archive finish, the low-level writer walks all retained `FileHeader` values,
slices the concatenated `file_names` buffer, writes central records, promotes
the tail to ZIP64 when required, writes EOCD, and flushes
(`crates/soapberry-zip/src/writer.rs:1429-1515`). The Office wrapper preserves
typed output progress if this final output fails (`office.rs:6624-6664`).

## What is allocated per Deflate member

The current low-level compressor is:

```text
OwnedCompressor::Deflate(
    DeflateEncoder<OwnedCompressedEntry<BoundedOutput<W>>>
)
```

(`crates/soapberry-zip/src/writer.rs:1707-1735`). In flate2 `1.1.10`,
`DeflateEncoder::new` constructs a fresh `Compress` and a fresh
`zio::Writer` (`registry/.../flate2-1.1.10/src/deflate/write.rs:29-44`). The
`zio::Writer` allocates a 32 KiB output `Vec` (`registry/.../flate2-1.1.10/src/zio.rs:10-15,173-179`).

flate2 does expose `DeflateEncoder::reset`, but its contract is to finish the
current stream into the current sink, reset the codec, replace the sink, and
return the old sink (`flate2-1.1.10/src/deflate/write.rs:69-89`). `finish`
instead consumes the encoder and returns its sink (`.../write.rs:110-128`).
That API does not separate compressor ownership from the current
`OwnedCompressedEntry`, whose `finish` must write the descriptor and append the
archive's central record. Calling `reset` is therefore not a mechanical change
to the current owned-entry stack, especially on an I/O or cancellation path.

With the selected `zlib-rs` backend, `Compress::new` allocates one contiguous
Deflate state block; the backend source explicitly documents that construction
allocates and should be used with care (`zlib-rs-0.6.7/src/stable.rs:294-321`).
The allocation is laid out from the private `State`, two windows, `prev`,
`head`, pending bytes, and symbol bytes with 64-byte alignment
(`zlib-rs-0.6.7/src/deflate.rs:321-356,3309-3373`). `Compress::reset` resets
the stream counters and backend state without dropping that allocation
(`zlib-rs-0.6.7/src/stable.rs:315-321`; `deflate.rs:745-805`); `Drop` calls
the backend deallocator (`stable.rs:412-415`).

The repository already has a direct fixed-buffer model in
`crates/soapberry-zip/src/preserve/replay.rs`. `ReplayPayloadWriter` owns one
`Compress` and a fixed 64 KiB input window (`replay.rs:729-786`), compresses
with a fixed output array and `FlushCompress::None`, checks input/output
deltas and no-progress statuses, and writes generated bytes through its
bounded accounting path (`replay.rs:923-1028`). Its finish loop uses
`FlushCompress::Finish` until `Status::StreamEnd` (`replay.rs:820-890`). It is
not a cross-member pool today, but it is an in-repository example of avoiding
flate2's allocating `zio::Writer` buffer while retaining explicit error and
progress handling.

## Smallest allocation-relevant reuse candidate

The narrow candidate is a private, single-entry reusable raw Deflate transport
state consisting of:

- one `flate2::Compress` configured exactly as the current path
  (`Compression::default()`, raw Deflate, `zlib_header = false`); and
- a fixed compressor output scratch buffer, with an input window only if the
  implementation needs stable chunking independent of caller write sizes.

The state would live with the streaming archive transport, be moved or
borrowed by one active Deflate entry, and be returned only after all final
compressed bytes and the ZIP data descriptor have been accepted. A successful
`Finish` reaching `Status::StreamEnd` would be followed by `Compress::reset`;
the Store path and persistent archive metadata would remain unchanged. The
direct `Compress` loop should follow the replay writer's explicit produced and
consumed delta checks rather than relying on `DeflateEncoder`'s implicit
`zio::Writer` buffer.

This candidate targets temporary compressor allocation work: backend state
construction/destruction and the per-entry output `Vec`. It does not claim that
the source audit has proven those allocations dominate the frozen batch. The
CPU and heap profiles must establish stack attribution before production work
is selected.

## Correctness obligations

### Admission and budgets

- Keep name validation, duplicate/equivalent/ancestor rejection, entry-count
  admission, metadata charging, and ZIP64 selection before the local header is
  emitted (`office.rs:6202-6255`; `phys_pkg.rs:946-1038`).
- Preserve the existing entry-size, aggregate-uncompressed, compressed-payload,
  and output-sink limits. A reusable codec's capacity is scratch state, not
  output-budget credit. Generated bytes must still pass the compressed-limit
  and `BoundedOutput` checks before they are accepted.
- Preserve accepted-byte accounting: uncompressed counters advance only by
  bytes accepted from the caller; compressed counters and output progress
  advance only by sink-accepted bytes. The final descriptor, central records,
  ZIP64 tail, EOCD, and flush remain subject to the output budget.

### Cancellation, poisoning, and drop

- A compressor may be returned to the reusable slot only after a complete
  successful Deflate finish, descriptor write, and entry reconstruction.
- Any codec error, compressed-limit error, sink error, `WriteZero`, or dropped
  incomplete entry must poison the operation as today and discard the active
  codec state. Reusing a partially finished stream risks carrying pending
  bits, history, counters, or buffered output into the next ZIP member.
- Do not depend on flate2's `zio::Writer` drop behavior to finish a failed
  stream. The `zio` drop path attempts to finish and ignores errors; this is
  incompatible with returning dirty state to a pool after a poisoned sink.

### CRC, framing, and progress

- Keep CRC32 over exactly the uncompressed bytes accepted by the entry. A
  direct compressor loop must preserve the current `ZipDataWriter` ordering
  when the codec consumes input or when the sink accepts only a prefix.
- Finish with `FlushCompress::Finish` until `Status::StreamEnd`; report an
  invalid-data/no-progress failure if no input or output progress occurs before
  completion. Emit no sync/full flush between ZIP members: every member needs
  an independent raw Deflate stream.
- Emit all final Deflate bytes before the data descriptor. Keep the descriptor
  CRC, compressed size, uncompressed size, and preselected ZIP32/ZIP64 width
  unchanged.
- Preserve the first source error and its typed limit/progress mapping in
  `capture_io_failure` and `finish_with_progress` (`office.rs:5398-5450,
  5456-5545`). Handle short writes and zero writes without looping forever.

### Determinism

Use the same Deflate level, raw-stream setting, entry order, XML fragments, and
effective input chunking as the current path. A direct `Compress` implementation
must compare complete archive bytes or hashes against the existing path for
representative inputs: changing caller-to-codec chunk boundaries can change a
Deflate bitstream even when the decompressed payload is identical.

## Temporary allocation work versus retained metadata

Compressor state and codec scratch are temporary transport work. Reusing them
can reduce repeated allocation calls and perhaps active operation peak, but it
does not remove the following retained structures:

- `ZipArchiveWriter.files: Vec<FileHeader>` and
  `ZipArchiveWriter.file_names: Vec<u8>` retain one central-record description
  and all raw member names until archive finalization
  (`crates/soapberry-zip/src/writer.rs:184-189,1429-1515`).
- `StreamingArchiveWriter.names: HashSet<String>` retains normalized ZIP member
  names (`office.rs:5326-5337`).
- `litchi_opc::PartNameSet.names` and `.descendants` retain folded PackURI and
  ancestor/descendant indexes; `PreparedPartName` also creates transient
  ancestor and descendant strings during admission
  (`crates/litchi-opc/src/phys_pkg.rs:946-1038`).
- Current PackURI/prepared-name values, central headers, and ZIP64 extra-field
  metadata have their own lifetime and accounting requirements.

`max_metadata_bytes` charges the transport's normalized names and generated
ZIP64 extra-field bytes; it does not represent allocator overhead for every
`Vec`, `HashSet`, `HashMap`, `FileHeader`, PackURI, or string. A directory spool
alone therefore cannot establish an output-independent heap bound while these
indexes remain in memory.

Replacing in-memory central-directory storage with a bounded caller-owned or
external spool would be a separate design. It would need to preserve central
record order and local-header offsets, duplicate/ancestor rejection, ZIP32/
ZIP64 tail decisions, output-budget enforcement, deterministic final output,
and error atomicity/progress. It should not be folded into a compressor-scratch
change or inferred from this audit.

## Audit conclusion

The source supports one focused reuse hypothesis: retain one successfully
resettable raw Deflate backend and fixed transport scratch across sequential
members, while treating all retained ZIP/OPC indexes as a separate memory
problem. The current source review does not provide measured owner attribution;
the frozen CPU and heap profiles must decide whether this candidate is worth an
implementation review.
