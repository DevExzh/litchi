# Change 0511 profile scope review

This is a read-only review of the 0511 CFB/OLE2 capture scope. It uses the
current `tools/perf-baseline/src/lib.rs`, `docs/performance/results/change-0413`
catalogs and profile evidence, and the 0511 capture wrapper. No build,
benchmark, or source edit was performed for this review.

## Exact invocations

The current wrapper uses `/tmp/litchi-goal-0511/<stage>/litchi-perf-baseline`
and writes reports below `docs/performance/results/change-0511/<stage>/`. A
normal child is run under `/usr/bin/time -v` and CPU 2. The nine XLS selectors
share one fixed comments/opaque-heavy corpus:

```text
/usr/bin/time -v taskset -c 2 \
  /tmp/litchi-goal-0511/after/litchi-perf-baseline \
  --case xls_semantic_open,xls_eager_open_list_worksheets,xls_eager_open_one_cell,xls_source_backed_open,xls_source_backed_open_list_worksheets,xls_source_backed_open_one_cell,xls_owned_source_open,xls_owned_source_open_list_worksheets,xls_owned_source_open_one_cell \
  --samples 1000 --warmup 20 \
  --json docs/performance/results/change-0511/after/xls-r1-report.json \
  --corpus-manifest docs/performance/results/change-0511/after/xls-r1-catalog.json
```

The `before` and `after` paths, output name, and stage are the only values
changed by the wrapper for the paired lanes. It intentionally omits
`--shape`, `--payload`, and `--writer-shape`: the XLS source and owned-source
selectors reject those overrides and use the fixed corpus. These are
in-memory generated fixtures, so the wrapper also leaves
`--filesystem-cache` at the harness default.

The two CFB/OLE2 guard shapes are a separate `cfb_open` run. The current 0511
scope selects incompressible payloads to match the retained 0413 guard:

```text
/usr/bin/time -v taskset -c 2 \
  /tmp/litchi-goal-0511/after/litchi-perf-baseline \
  --case cfb_open --samples 1000 --warmup 20 \
  --json docs/performance/results/change-0511/after/guard-r1-report.json \
  --corpus-manifest docs/performance/results/change-0511/after/guard-r1-catalog.json \
  --shape tiny,few-large --payload incompressible
```

This produces one `cfb_open` row per shape. Before formal captures, root
changed the initially planned compressible arm to incompressible to retain
the historical guard workload. Fresh corpus identities are validated by the retained replay.
The retained 0413 rows were
`cfb-tiny-incompressible` (3,584-byte archive, 512-byte target) and
`cfb-few-large-incompressible` (16,912,384-byte archive, 4,194,304-byte
target).

The bounded Callgrind lane generated by the current wrapper is:

```text
/usr/bin/time -v valgrind --tool=callgrind \
  --collect-atstart=no \
  '--toggle-collect=*SourceBackedWorkbook::from_read_at_with_limits' \
  --callgrind-out-file=docs/performance/results/change-0511/after/callgrind.out \
  /tmp/litchi-goal-0511/after/litchi-perf-baseline \
  --case xls_owned_source_open_one_cell --samples 5 --warmup 0 \
  --json docs/performance/results/change-0511/after/callgrind-report.json \
  --corpus-manifest docs/performance/results/change-0511/after/callgrind-catalog.json
```

The wildcard is quoted for a shell invocation. `capture.py` passes it as one
argument and does not add `taskset` to this diagnostic lane. The exact target
is the `_with_limits` body; a broad `*from_read_at*` pattern should be avoided
because it can match both the wrapper and its nested `_with_limits` call.

## Corpus and binding evidence

The 0413 normal catalog has one corpus and nine case bindings. Its corpus is
`xls-cfb:sha256:6a57231ba681bc7dd38d447ebd5348ef3b1fefedeefb1e61c97f22faa074e53`,
named `xls-comments-opaque-heavy`: 16,995,840 archive bytes, 80,946
Workbook-stream bytes, two ordinary worksheets, and an opaque payload. The
nine bindings are exactly the selectors in the first command. This establishes
that the eager, instrumented source-backed, and plain `OwnedSource` rows are
matched on corpus identity; the generated 0511 catalog remains authoritative
for its own provenance hash.

`build_xls_source_layout` independently reconstructs the CFB FAT/directory and
Workbook physical ranges, checks the `BoundSheet8` inventory, and uses eager
`Workbook::new` to establish worksheet names, cell count, and the selected
numeric cell. That work is before the per-sample timer. The 0413 profile and
change record also establish that source counters are logical `ReadAt` ranges,
not physical I/O, and that whole-process RSS/PMU observations include setup
and post-operation work.

## Timer and oracle boundaries

The three runner families have these scopes:

| Family | Measured region | Outside the timer |
| --- | --- | --- |
| `xls_semantic_open`, `xls_eager_open_list_worksheets`, `xls_eager_open_one_cell` | eager `Workbook::new` plus the selected open/list/cell operation | archive clone, layout construction, names/value oracles, allocation close, digest and report work |
| `xls_source_backed_open`, `xls_source_backed_open_list_worksheets`, `xls_source_backed_open_one_cell` | `SourceBackedWorkbook::from_read_at` plus the selected operation | `InstrumentedSource` construction, version probe, layout construction, post-operation source counter/locality checks, lifecycle oracles and drop |
| `xls_owned_source_open`, `xls_owned_source_open_list_worksheets`, `xls_owned_source_open_one_cell` | `SourceBackedWorkbook::from_read_at` plus open/list/selected-cell query | `OwnedSource` construction and clone, pre-version probe, layout construction, post-version probe, digest/oracle checks and drop |

For the owned runner, the source setup is at `run_xls_owned_source_case`
before `Instant::now`; the constructor starts at the timer and the query ends
it. The source-backed runner has the analogous boundary around its
`InstrumentedSource` operation. `cfb_open` starts the timer immediately before
`OleFile::open(Cursor::new(...))` and stops immediately after it; the file-size
oracle is after the stop.

## Can the Callgrind toggle isolate the operation?

It can isolate the constructor portion for the current diagnostic case. The
owned one-cell path calls `build_xls_source_layout` before the loop, and that
layout uses eager `Workbook::new`, not `SourceBackedWorkbook`. Each measured
iteration then enters `from_read_at`, which immediately calls
`from_read_at_with_limits`. With collection disabled at start, Callgrind turns
collection on at that exact function entry and off at return. Therefore the
selected-cell query (which is still part of the `Instant` timer), source setup,
the version/digest/oracle checks, report serialization, and final drop are not
collected by this toggle.

The scope is narrower than the timed one-cell operation: it is constructor CPU
attribution, not a full operation latency or allocation/RSS measurement. A
toggle cannot collect the entire `Instant` region with the current harness
because there are no phase markers around the timer. The 0413 profile should
remain the warning for interpretation: it was whole-process `cycles:u`
attribution, and its observed `OwnedSource::read_at` and CFB/XLS ancestors did
not prove operation-local cost.

The source-level call tree to inspect under the toggle is:

```text
<litchi_xls::workbook::source::SourceBackedWorkbook>::from_read_at
  <...SourceBackedWorkbook>::from_read_at_with_limits       # toggle target
    <litchi_cfb::shared::SharedOleFile>::open_with_limits
      <litchi_cfb::shared::SharedOleFile>::open_source_with_limits
        <litchi_cfb::file::OleFile<litchi_cfb::shared::ReadAtCursor>>::open_with_limits
          load_fat
          load_directory
          load_minifat
          validate_stream_allocations
          validate_physical_sector_layout
          read_sector_into
    <...SourceBackedWorkbook>::from_shared_ole_file_with_limits
      litchi_xls::workbook::source::parse_globals
      <litchi_cfb::shared::SharedOleStreamCursor>::read_exact
```

Instrumented source callbacks execute inside the source-backed operation clock.

The control source locus is `litchi_cfb::file::OleFile::load_fat`: it computes an
exact fallible FAT-entry reservation and then still calls the generic
`litchi_cfb::file::try_push::<u32>` for each entry. `SectorChainScratch::collect_exact`
and `try_push::<u32>` are both visible in the 0413 one-cell profile, but the
generic helper has several callers; a `try_push` sample cannot be attributed to
FAT construction without its `load_fat` ancestor. `load_minifat`,
`SectorChainScratch::collect_exact`, and `validate_stream_allocations` are
separate descendants and should remain visible in the review.

The appropriate conclusion from a nonzero Callgrind target and its descendants
is therefore “constructor attribution for this fixed owned XLS case.” It does
not support a claim about the full selected-cell timer, CFB guard latency,
physical I/O, or broad XLS/OLE2 performance.
