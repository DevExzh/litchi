# Change 0482 measurement review

Independent review of the frozen raw evidence is complete. The 24 report
files contain 720 measured samples: three source sizes, two routes, two
instrumentation binaries, two repeats, 30 samples per row, and three warmups
per process. All 720 samples succeeded. Every report's generator oracle
verified the actual byte count and SHA-256, and every successful report had
the expected semantic fields. The 360 allocator samples all ended with zero
net live bytes and no failed allocation calls.

The raw reports were recalculated independently with `n = 30`,
`t(29) = 2.045229642`, a sample-standard-deviation confidence interval for
the mean, and nearest-rank p50/p95/p99. The recalculated values match
`summary.json` exactly. The tables below use milliseconds and KiB; RSS is
the GNU `time -v` process maximum from each capture's resource sidecar.

## Scope and control limitations

The materialized route is a named harness control: it creates the same
deterministic source, calls `read_to_end` into a `Vec<u8>`, audits the slice
with `verify_authored`, and drops the owned source inside the timed scope.
The streaming route feeds the same generator through a fixed 16 KiB
`BufRead` window to `verify_authored_reader`. Both timed scopes include
generator construction, source production, auditing, and owned drops;
independent digest/layout oracle setup is outside the timed regions.

The generator's byte/layout work is therefore counted in both routes and may
dominate small-input CPU time. Whole-process RSS includes startup, oracle
setup, warmups, measured samples, report serialization, and teardown; it is
not an operation-local or per-sample memory measurement. The materialized RSS
difference demonstrates the cost of this control's `read_to_end` capacity
growth, while the scoped allocator counters demonstrate the route-local
allocation pattern. Neither establishes constant RSS for every caller or a
DOCX/OPC append, preservation, repeated-transaction, or end-to-end
performance claim.
