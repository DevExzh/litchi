## For `HOTSPOTS.md`

## 0625 — the OLE2 writer's directory order was a hash seed; it is now a function of the document

Not a hotspot: a correctness defect on the hottest OLE2 write path, reported by change [0617](0617-cfb-copy-through-writer-design.md) and fixed here. `OleWriter::write_to` iterated `self.storages: HashSet<Vec<String>>` to call `DirectoryBuilder::add_storage_path`, which assigns `sid = entries.len()`, with entries serialized in SID order — and `link_children` then builds each parent's red-black sibling tree by inserting `child_sids` in that same SID order, so the hash seed decided the tree's shape and colours as well as the numbering. Rust seeds a `HashSet`'s hasher per instance, so **the same document serialized to a different file on every run**. Measured at this batch's base commit before anything changed, change 0617's synthetic document gives **1, 2, 6 and 64 distinct outputs in 64 in-process builds at 1, 2, 3 and 8 storages**, reproducing 0617's separate-process digests exactly; six at three storages is 3!, every permutation of the sibling SIDs. The defect needs two storage paths neither of which is a prefix of the other, because `add_storage_path` creates missing ancestors on the way down a path, and streams are unaffected because `self.streams` is a `Vec` whose insertion order is a deliberate part of the model. Over the repository's **214 CFB fixtures**, 8 qualify and all 8 were non-deterministic (2 to 16 distinct digests in 16 rebuilds) — `TestZeroLengthCodePage.mpp` at 18 storages, `WithEmbeddedObjects.xls` at 11, `59858.xls` at 10, `word_with_embeded.doc` at 5, and four three-storage spreadsheets. `write_to` now sorts both the storage table and the storage-CLSID table by **depth, then component-wise lexicographic order of the stored spellings** — the order `litchi-ole-common`'s `Package::render` already computed before calling `create_storage` and the writer then threw away, so on every length-changing XLS, DOC and PPT save the emitted directory is now the one the renderer intended. After: **one digest everywhere**, 203 of 203 already-deterministic fixtures byte-identical, 0 length changes in 211. The cost is one `O(n log n)` sort and two bounded allocations per save: **+78 Ir** on a storage-free 984 KB XLS rebuild (exact; both legs bit-reproducible) and **+1,493 Ir** on a five-storage DOC (inside that case's own 1,046-1,396 Ir repetition spread). `performance_claim: none`; nothing got faster and no claim is registered. OLE2/OOXML remain active; ODF is deferred until completion and iWork excluded. [Record and limitations](0625-cfb-writer-deterministic-storage-order.md); [retained evidence](results/change-0625/README.md).

## For `GOAL_AUDIT.md`

## 0625 — `docs/GOAL.md`'s determinism requirement, restored on the OLE2 write path

`docs/GOAL.md` puts correctness, lossless preservation and bounded resources above speed, and ADR 0006 states the rule this change restores: *"Serialization is deterministic unless a `Clock`, actor identity, or cryptographic RNG is explicitly supplied."* `OleWriter` is supplied none of the three and was non-deterministic anyway, through hash-table iteration order rather than through any declared source of entropy — which is why no audit row had caught it and why change 0617 only found it by digesting the same build twice. Every OLE2 writer in the workspace reaches this code: `Package::render` in `litchi-ole-common`, behind every length-changing XLS, DOC and PPT save; the custom-XML codec; `litchi-crypto`'s encrypted-OOXML container writer and its `rebuild_ole`; `litchi-vba`'s project writer; `litchi-sign`'s CFB signature writer; and `litchi-ograph`'s package writer. The fix is confined to `write_to` and is chosen so that no other contract moves: the canonical order is infallible, so no refusal changes identity or position; it is total over the distinct keys of a `HashSet`, so it needs no tie-break; it places every ancestor ahead of its descendants, which is what `add_storage_path` wants; and it keeps the two hash tables, so `create_storage` keeps the `try_reserve` allocation-failure path that `reserve_hash_set_entry` exists to provide. Three alternatives were considered and are recorded with why they lost: the MS-CFB sibling key via `canonical_cfb_path` (fallible — it would move a refusal), `BTreeSet`/`BTreeMap` fields (no `try_reserve` — it would abort instead of returning `OleError::Allocation`), and an insertion-ordered collection matching `SequentialOleWriter` (linear duplicate check, so *n* storages become O(*n*²) under adversarial control, and the output would be a function of the call history rather than of the document). Two audit rows this change opens: the corpus differential is writer-level rather than save-level, so a digest-comparing differential through each format crate's own editor would be a strict upgrade; and `SequentialOleWriter`, which is already deterministic, still uses declaration order, so the two writers agree only for callers that sort. No latency, RSS, allocation or throughput improvement is claimed by this batch; the change makes a save very slightly more expensive. OLE2/OOXML remain active; ODF is deferred until completion and iWork excluded.

## For `REPORT.md`

## 0625 — the same document, the same bytes

Change 0625 fixes the defect change 0617 found and reported: `OleWriter::write_to` assigned directory SIDs by iterating a `HashSet`, so a document with two or more storage paths neither of which is a prefix of the other produced a different file on every run. The fix is 47 inserted lines in one file — `write_to` copies both the storage table and the storage-CLSID table into bounded local vectors, sorts them by depth and then by their stored path components, and iterates those — plus a new six-test file that is the oracle. Three of those six tests fail on the unmodified writer (64 distinct outputs in 64 builds at eight sibling storages, 38 in 64 for a nested case, and a declaration-order test) and three pass on both legs, because they encode what must not change: the one-storage output still digests to change 0617's 2,560-byte value, and the deterministic output still reopens through `OleFile` with every storage and stream readable. Beyond the unit oracle, every one of the 214 CFB artifacts under `test-data/` was reduced to its logical model through the public parser and rebuilt through `OleWriter` sixteen times on each leg: 211 rebuild, 3 refuse identically on both, 8 were non-deterministic before and **none after**, and all **203** that were already deterministic are **byte-identical**, with no length change on any of the 211. Instruction cost, by callgrind isolation pairs at 2 and 12 rebuilds with three repetitions per leg: **+78 Ir** per rebuild on `54016.xls` (no storages, both legs bit-reproducible) and **+1,493 Ir** on `word_with_embeded.doc` (five storages), the second inside its own repetition spread. No wall-clock measurement was taken and none would resolve it. Gates: `cargo fmt --all --check` clean, Clippy clean on `litchi-cfb` with all targets, `cargo doc` clean, `cargo test -p litchi-cfb` 322 + 13 + 6 + 6 passed with 12 doctests and 1 ignored, `cargo test` over `litchi-xls`, `litchi-doc` and `litchi-ppt` **3,779 passed, 0 failed** across 145 test binaries, and `cargo test` over the five other crates that call `create_storage` — `litchi-ole-common`, `litchi-crypto`, `litchi-vba`, `litchi-sign`, `litchi-ograph` — **312 passed, 0 failed**. `performance_claim: none`: this change costs instructions rather than saving them. [Change and limitations](0625-cfb-writer-deterministic-storage-order.md); [retained evidence](results/change-0625/README.md).

## For `ADR_COMPLIANCE.md`

## 0625 — ADR 0006's determinism clause, restored rather than reinterpreted

This change exists to satisfy one sentence of ADR 0006: *"Serialization is deterministic unless a `Clock`, actor identity, or cryptographic RNG is explicitly supplied."* `OleWriter::write_to` supplied none of the three and was still non-deterministic, because it read `self.storages: HashSet<Vec<String>>` and `self.storage_clsids: HashMap<…>` in hash iteration order to assign directory SIDs, and `generate_directory_stream` serializes entries in SID order while `link_children` builds the red-black sibling trees by inserting children in it. Change 0617 confirmed the violation by execution and reported it; this change removes it, and the before leg here reproduces 0617's digests exactly at a different base commit. Nothing else in the ADR set moves. ADR 0026's directory metadata binding is untouched: no field of any directory entry is computed differently, only the order in which entries are created, and `DirectoryBuilder` still derives and validates the whole red-black tree the same way, so the ADR's "state bits and timestamps are intentionally not fabricated" is unaffected. ADR 0005's bounded-resource rule is honoured rather than traded: both new vectors are reserved with `try_reserve_exact` and mapped to the writer's existing `OleError::Allocation { resource, source }`, `sort_unstable_by` is in-place, and the two hash tables are deliberately kept so that `create_storage` retains the `try_reserve` failure path a `BTreeSet` would have removed. ADR 0003's preserve default is unaffected, because this path is the from-scratch builder. Error identity is preserved deliberately and is the reason the MS-CFB sibling comparison was **not** used as the sort key: `canonical_cfb_path` re-validates each component, so an over-long or forbidden storage name that `create_storage` accepts and `DirectoryEntryBuilder::storage` refuses later would have been refused earlier in `write_to` and, for the over-long case, with a different message — a contract change for no gain. One refusal does become deterministic without moving: two storage paths whose names are CFB-equal but differently spelled still fail `ensure_unique_child` with `duplicate CFB sibling name`, in the same place and with the same variant, but the name in the message no longer depends on the hash seed. Validation is neither added nor relaxed: `validate_stream_size`, `ensure_unique_child`, `validate_child_tree`, `FatBuilder::validate` and `validate_output_size` all run exactly as before, and the three fixtures the parser refuses are refused identically on both legs with the same error text. No `unsafe`, no limit widened, no I/O added. `performance_claim: none`. OLE2/OOXML remain active; ODF is deferred until completion and iWork excluded.
