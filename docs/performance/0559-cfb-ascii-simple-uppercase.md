# 0559: ASCII fast path for the CFB simple uppercase mapping

Status: retained. `performance_claim: none` — this record carries paired and
deterministic measurements, not a registry claim.

OLE2 and OOXML remain the active priority. ODF optimization stays deferred until
that goal completes; iWork is excluded.

## What changed

`[MS-CFB]` 2.6.4 orders directory-entry names by their *simple* uppercase
mapping. Both owners computed that mapping with `char::to_uppercase`, which
constructs a Unicode case-mapping iterator for every scalar and then discards
the result when the mapping expands to more than one scalar:

- `crates/litchi-cfb/src/directory_name.rs` — `simple_uppercase`, reached from
  `directory_name_data`, which every directory-entry lookup and every written
  directory entry calls;
- `crates/litchi-ole-common/src/object/cfb_path.rs` — the same computation
  inlined in `UppercaseUnits::next`, now factored into a shared
  `simple_uppercase` helper in that module.

Both now return `character.to_ascii_uppercase()` directly when the scalar is
ASCII, and fall through to the original Unicode path otherwise.

## Why it is exactly equivalent

No ASCII scalar has a multi-character uppercase mapping, and every ASCII
scalar's single-character mapping is its ASCII uppercase. The ASCII branch
therefore returns precisely what the general path returned, so comparison keys,
ordering, duplicate detection, and refusals are unchanged.

This is proved, not sampled:
`uppercase_matches_unicode_mapping_for_every_char` in each owner iterates the
**entire Unicode scalar range** and asserts the new function equals a local copy
of the original implementation for every code point. Additional tests pin the
encoded comparison keys for representative ASCII and non-ASCII names
(including `ß`, `ﬁ`, `İ`, final sigma, and an astral scalar), the four refusal
cases, and ASCII case-insensitive equality.

## Why it was measured

Change [0558](0558-ole2-single-read-fence.md) left a reproducible latency
regression on `ole_common_one_edit_save` whose instruction count was unchanged.
Deterministic Callgrind branch simulation attributed 70,571 of its 72,538
additional conditional branch misses — and 205,732 of the pre-0558 baseline's
660,113 total — to `<core::char::ToUppercase as Iterator>::next`. The hotspot
was therefore pre-existing and layout-sensitive, not created by 0558.

### Neutrality on the source-backed XLS path

Two repeats of A1/B1/B2/A2 over the same 48-child protocol used for 0558, with
0558 as the baseline stage, confirm this change does not touch freshness or
source work: `version()` calls, `statx` counts, `read_at` calls and read bytes
are byte-for-byte identical in all six cells, and p50 moves within ±1.63% with
no consistent direction. That path performs few directory-name comparisons, so
no improvement is expected or claimed there.

### Confirmation against the final source

Three post-build edits landed after the staged ABBA binaries were produced:
rustfmt rewrapping inside `#[cfg(test)] mod tests`, one doc-comment clarification
in `shared.rs`, and one repaired doc comment in `cfb_path.rs`. None reaches
release codegen, and Rust release builds are not bit-reproducible on this host,
so identity was re-established by measurement rather than by binary hash. A
binary built from the final source, compared with the pre-0558 baseline binary on
the same host and corpora, reproduces the result:

| Case | tiny | many-small | few-large | wide-root |
| --- | ---: | ---: | ---: | ---: |
| `cfb_open` | −14.16% / −15.65% | −19.39% / −19.59% | −0.69% / −0.63% | −22.63% / −22.67% |
| `ole_common_one_edit_save` | −22.68% / −22.46% | −16.66% / −25.90% | +0.18% / +0.53% | −33.41% / −33.49% |
| `ole_common_finish_render` | −25.91% / −25.82% | −14.37% / −14.50% | −0.28% / +0.14% | −34.56% / −34.99% |

Each cell shows the compressible and incompressible payload corpora. The
`few-large` corpora hold few directory entries and stay within ±0.7%. The

Hashes and the full table are in

## Correctness evidence

All ten final quality gates pass: 4,238 tests in the OLE2 crates and 4,325 in
the OOXML crates, with zero failures, plus warning-denied Clippy and rustdoc,
formatting, the all-feature workspace check, minimal-feature checks, crate
boundaries, and the strict claim registry. `litchi-cfb` gains four tests and
`litchi-ole-common` two, including the two exhaustive per-scalar equivalence
proofs. See [`quality.md`](results/change-0559/quality.md).

## Limitations

No cold-cache, physical-device, remote/range-source, peak-RSS, allocation,
concurrency-scaling, real-producer, or cross-platform result is claimed. Names
that are not ASCII take one extra predictable branch before reaching the
unchanged Unicode path; no corpus in the matrix exercises a non-ASCII directory
name, so that cost is bounded by inspection rather than measurement.
