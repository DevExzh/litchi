# Deterministic corpus manifest schema 2

The performance report schema and the `results[*].corpus` object are frozen at
schema 1.  Schema 2 is an additive catalog for corpus provenance and coverage;
it may be emitted as a sidecar with `--corpus-manifest PATH` and referenced from
the report by the optional `corpus_catalog` object.  Existing reports,
comparisons, and the checked schema-1 case/corpus identity remain valid.

The normative JSON Schema is
[`schemas/corpus-manifest-v2.schema.json`](schemas/corpus-manifest-v2.schema.json).
The checked default catalog is
[`results/perf-corpus-manifest-v2.json`](results/perf-corpus-manifest-v2.json).

## Identity and canonicalization

Every corpus has a content-addressed ID:

```text
<normalized-package-format>:sha256:<lowercase archive SHA-256>
```

The archive hash is over the exact input bytes.  Member hashes, when available,
are over logical member bytes; malformed or unparseable inputs may use
`members.status = "unavailable"` while retaining the raw archive hash.

`catalog_sha256` is SHA-256 over the compact UTF-8 JSON catalog with the
`catalog_sha256` property removed.  Object keys are sorted lexicographically;
corpus entries are sorted by ID and case bindings by `(case, corpus_id)`.
There are no timestamps or host-dependent paths in a deterministic catalog.

`content_set_sha256` covers only corpus IDs, archive/member hashes, and case
bindings.  It is therefore stable when a report is regenerated by a different
revision of the harness while `catalog_sha256` still records all provenance and
generator metadata.

## Required truthfulness rules

Schema 2 distinguishes absence from missing evidence.  V1 migration sets
security, producer, relationship, malformed-input, and read-limit fields to
`unknown`/`null` unless the source report actually recorded the fact.  A
synthetic refusal fixture must use security evidence such as
`"synthetic-guard"` and a `guard_cases` binding; it must not be described as a
valid signed, encrypted, or macro-enabled Office document.

Producer records use repository-relative source paths and content hashes.
Licenses are recorded only with evidence; an unannotated fixture has a null
license and is not silently treated as redistributable.

Generator records include an identifier, revision, algorithm/seed fields, and
deterministic parameters.  V1 migration leaves algorithm and seed fields null
because those facts were not present in the V1 object.

## Migration contract

`tools/perf-baseline/src/corpus_manifest.rs` owns the Rust migration and
canonical hashing implementation.  `tools/generate_corpus_manifest_v2.py`
performs the same conservative migration for checked documentation artifacts.
The following invariants are tested:

- projecting a migrated V2 entry's `legacy_v1` value reproduces the V1 corpus
  object exactly;
- old reports without `corpus_catalog` remain accepted;
- adding a V2 reference does not change the schema-1 result-key digest;
- duplicate content IDs and case bindings fail closed;
- catalog hashes are independent of input record order;
- missing metadata remains explicitly unknown.

The V1 identity artifact
`results/perf-regression-default-manifest-v1.json` is intentionally not
rewritten.  Adding or changing V2 metadata does not authorize a new latency
claim; the existing comparator still gates the exact schema-1 case/corpus keys.
