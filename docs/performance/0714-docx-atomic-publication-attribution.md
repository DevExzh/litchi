# 0714 — DOCX atomic publication attribution

Status: current-source diagnostic; no production or harness change and no
before/after performance claim. Scope: the two named ordinary DOCX corpora,
four native phases, and separate publication traces on this machine.

The fresh native observations place atomic publication p50 at 5.20–5.37 ms
and counting-sink publication at 0.122–0.336 ms. In each separately traced
measured atomic transaction, the archive reaches the sibling temporary file
in one write, followed by file sync, replacement rename and parent-directory
sync. This establishes the syscall boundary for further work while preserving
the publication contract. It does not establish a native syscall fraction or
a physical durability floor.

## Trace attribution

Each atomic trace contains four setup publications with destination sequence
`published.docx`, `published.docx`, `published-repeat.docx`, `published.docx`.
Both setup destinations are removed before the fifth, measured publication.
Each counting control contains only those four setup publications. Whole-child
syscall totals would include setup, readback, cleanup and JSON reporting and
are therefore excluded from attribution.

The parser follows temporary paths and descriptors through writes, file sync,
rename, parent-directory open/sync/close and persisted-file close. Output byte
counts equal the corpus evidence: 9,070 generated bytes and 55,123 NumberedList
bytes. The measured destination probe returns ENOENT, with no permission-copy
`fchmod`. These measured transactions cover creation at a removed destination;
they do not measure replacement of an existing destination with permission
preservation. Destination readback and unlink lie outside the selected window.

Trace durations below are milliseconds and include tracer perturbation. The

only the sum of the two sync durations divided by that same trace's window;
it is not divided by an independently sampled native latency.

## Next optimization boundary

The source path in `crates/litchi-opc/src/atomic.rs` already uses a 64 KiB staging
buffer and requires flush, temporary-file `sync_all`, replacement and parent
sync. A proposed syscall-batching change must account for the observed single
archive write. Removing either successful sync would change the contract and
is not an optimization candidate for this workflow.

The next bounded CPU investigation is ordinary serialization through DOCX
`write_plain`, `OpcPackage::to_stream` and `PackageWriter::write_counted`, with
attribution to materialization, preserved-member handling and changed-member
compression. `try_write_preserved` already exists; unchanged-member passthrough
is not a new proposal. The counting-sink phase supplies a separate CPU-oriented
workload for profiling, but this packet supplies no serialization-owner profile
or speedup claim. Existing edit profiles from 0713 remain evidence for their
own scope only. The non-iWork program goal remains active.
