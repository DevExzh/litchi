# ZIP operation accounting

## Status

This is a production `soapberry-zip` correctness slice. It defines and
exposes operation-local byte accounting for the covered single-entry,
convenience, and preservation paths. Existing public API contracts and
archive-writing behavior remain unchanged; the accounting is additive and
does not change the bytes accepted or emitted by an operation.

```text
performance_claim: none
```

The counters are logical operation counters. They are not a benchmark,
resource profile, or acceptance gate. This record makes no claim of benchmark
acceptance, a speedup, a regression improvement, or a performance baseline.

## Counter meanings

The counters below are intentionally separate. A declared ZIP size, a member
payload size, bytes produced by a codec, bytes accepted by a sink, and bytes
copied for preservation are not interchangeable measurements.

| Counter | Meaning | Boundary |
| --- | --- | --- |
| Deflate compressed source read | Compressed Deflate member-payload bytes actually read by the Deflate source/decode operation. | Counts the compressed data range traversed by the operation, not the declared central-directory size. It excludes ZIP local headers, data descriptors, central-directory records, end records, and comments. On a typed failure it is the partial amount read before the failure. |
| Store source bytes | Store member-payload bytes supplied by the source. Store has no codec expansion, so these are also the logical uncompressed payload bytes. | Counts member payload only, not ZIP framing or metadata. |
| Store accepted bytes | Store payload bytes accepted by the destination/sink. | It can be lower than Store source bytes on a short write or sink failure; on successful completion the two values match. |
| Deflate produced bytes | Uncompressed bytes produced by the Deflate decoder. | Counts decoder output made available to the operation, whether or not the destination has accepted every byte. |
| Deflate accepted bytes | Decoded Deflate bytes accepted by the destination/sink. | It is bounded by Deflate produced bytes and can be lower on a short write or sink failure. On successful completion it equals the produced payload. |
| Generated Deflate | Compressed member-payload bytes generated by a Deflate compressor for a newly generated member. | Counts compressor output only. It excludes local headers, data descriptors, central-directory records, end records, and comments. |
| Stored emitted | Member-payload bytes emitted for a newly generated Store member. | Counts the stored payload only and excludes ZIP framing and metadata. |
| Precompressed emitted | Caller-provided compressed member-payload bytes emitted without recompression. | Counts the precompressed payload only and excludes ZIP framing and metadata. |
| Raw unchanged accepted | Bytes accepted while copying an unchanged raw ZIP representation through the preservation path. | This is archive-byte accounting rather than payload accounting. It includes unchanged member data, ZIP framing, descriptors, central-directory/end records, and the archive comment when those bytes are part of the copied representation. |

`source` counters describe bytes obtained from or supplied to the operation;
`produced` and `emitted` counters describe bytes made by a codec or writer;
`accepted` counters describe bytes accepted by the destination. A successful
operation may make related counters equal, but the equality is not assumed for
partial operations or failures.

The counters do not silently substitute declared metadata for observed byte
movement. In particular, a central-directory compressed-size field is not a
Deflate compressed-source-read observation, and an archive output size is not
a generated or precompressed member-payload observation.

## Operation-local provenance

Each accounting result is interpreted in the context of the operation that
produced it. The provenance identifies the archive/member operation and its
implementation path, the Store or Deflate method, the declared member sizes,
the source and destination boundary, and whether each value is a payload
counter or an archive-byte counter. It also retains the operation outcome so
that partial values from a typed decode, limit, short-write, or sink failure
are not mistaken for successful totals.

The provenance is local to the operation. It does not describe process-wide
I/O, allocator, or scheduler activity, and it does not turn the counters into
ambient instrumentation. A value labelled accepted is a destination/sink
observation, not a claim that the operating system performed a physical write.

## Covered production paths

The first slice covers:

- single-entry Store and Deflate read/decode operations, including the
  materializing and destination/sink convenience forms;
- single-entry generated Store and Deflate output, including caller-supplied
  precompressed output where that convenience path is used; and
- preservation output through `PreservationIndex::write_to`, including the
  raw unchanged copy path and its framing/comment bytes.

The existing archive formats, error handling, limits, and output contracts are
unchanged. The accounting only records the boundaries of the operation that
already takes place.

## Deferred work

This slice intentionally does not cover or claim to solve:

- `StreamingArchiveEntry` accounting and its aggregate writer integration;
- parallel or bulk-entry accounting;
- OPC-level propagation or interpretation of ZIP counters;
- `operation_metrics`/report schema changes, comparator identity rules, or
  performance-baseline policy;
- a new performance-harness selector, default-case changes, ABBA evidence, or
  benchmark acceptance.

Those pieces require separately reviewed counter schemas and provenance rules.
They must not infer physical or process-level measurements from these logical
operation counters.

## Explicit exclusions

No performance claim is made for:

- physical I/O or filesystem behavior;
- syscall counts or syscall latency;
- RSS, peak memory, or other process-resource measurements;
- allocations, deallocations, or allocator traffic;
- zero-copy behavior or the absence of materialization/copying; or
- throughput, latency, speedups, regressions, or any other benchmark result.

`performance_claim: none` remains the authoritative status for this slice.
