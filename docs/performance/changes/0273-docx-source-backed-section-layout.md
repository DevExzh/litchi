# Change 0273: DOCX source-backed existing-section layout

Date: 2026-08-24

Status: correctness and CRUD closure; `performance_claim: none`

## Scope

The new opt-in selector
`docx_source_backed_existing_section_layout_edit_save` exercises one
existing main-story section on a fixed DOCX/OPC/ZIP corpus. The typed snapshot
and edit surface covers `PageSize`, `Margins`, `Start`, and `Columns`
through commit, durable patch/inverse, and sequential publication. Table-cell
sections are excluded. Unsupported structural column edits typed-refuse; this
closure does not add insert/remove operations or header/footer relationship
editing.

Section lookup uses one bounded namespace scan. Expanded-name matching selects
the exact XML splices, including default-namespace documents. Clearing a field
refuses opaque content rather than approximating it. SourceLineage and the
source fingerprint remain bound through snapshot, commit, publication, stale
checks, and durable inverse application.

The selector takes the selectable matrix to **393 names** while the default
remains **36 cases / 198 records**. Signed-source refusal, stale-source
refusal, partial-sink behavior, strict source/output identity, and default
namespace tests remain required correctness gates.

## Correctness boundary

The operation retains phase vectors for the existing snapshot/edit/commit and
sequential publication path. Source lineage/fingerprint, exact expanded-name
splices, semantic reopen, durable Publication inverse, signed/stale refusal,
partial-sink behavior, and strict source/output identity are oracles rather
than performance claims. The default-namespace variant is checked separately
from prefixed input, and opaque section content is refused for clear/edit
operations where the typed model cannot prove a safe splice.

## Exploratory smoke and profile

A dirty CPU-2 smoke used one warmup and five samples. Median total time was
4.826203 ms, with query at 1.256769 ms and publication at 2.932747 ms. Logical
counters and the 34.3 MiB whole-process RSS observation are descriptive only;
they are not operation-local or allocator measurements.

A separate dirty five-sample `perf` profile retained 1,920 `cycles` samples
with no lost samples. The reported samples attributed 31.90% to `sha256`,
15.26% to `payload_bytes`, 6.56% to `memcmp`, 5.78% to `memmove`, 2.57%
to `NsReader process_event`, and 2.10% to Inventory parsing. The profile is
whole-process and contaminated by corpus setup and correctness oracles; it is
prioritization evidence only and does not establish a production hotspot,
latency result, or resource result.

No claim is made for physical I/O, allocator behavior, RSS/peak memory,
decompression, copy volume, or broad DOCX performance. No claim-registry entry
or historical classification is updated.
