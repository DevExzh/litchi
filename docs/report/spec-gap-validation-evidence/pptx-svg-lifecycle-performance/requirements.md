# Source-backed PPTX SVG lifecycle profile requirements

This evidence batch measures the source-backed SVG attach/detach lifecycle after
the production owner is frozen. It is an absolute, scenario-scoped profile; it
does not compare against an older implementation or claim native Office
acceptance, rendering performance, or a general PPTX performance result.

The profile must use three fresh processes and at least twenty measured samples
per lane after warm-up. Every sample records elapsed wall time, direct allocation
and reallocation accounting, incremental peak live bytes, and the process RSS
reported by `/usr/bin/time -v`. A process-local counting allocator must verify
that all allocation deltas balance and that no allocation failed or underflowed.

The final matrix should include representative small and large source-backed
PPTX inputs and the following named operations:

- capture of an existing raster picture with no SVG and capture of an existing
  SVG picture;
- capture of a namespace-heavy source with 252 inherited bindings and 1,024
  opaque descendants, plus a syntactically complete source that is refused at
  the owner resolver's 16,384 active-binding ceiling;
- full-slide raster inventory for 256 and 1,024 direct pictures sharing one
  raster relationship, with every returned descriptor checked; these lanes
  expose repeated owner-resolution work without a linear-scaling claim;
- paired 256 and 1,024-picture inventory with one distinct local namespace
  declaration per picture, retaining the relationship and payload workload
  while exercising local namespace-context capture;
- attach, commit, publish, and reopen for small and large SVG/raster payloads;
- detach, commit, publish, and reopen for small and large SVG/raster payloads;
- the exact no-op publication path and cheap clone/patch operations;
- malformed relationship/markup and caller-limit refusal paths.

Fixture construction and semantic assertions must remain outside the timed
closure where the lane is intended to isolate one owner operation. End-to-end
lanes include the explicitly named sequence (`capture`, fallible `commit`,
`publish`, `reopen`) and must report that scope in the result schema. The
fallible `commit()` closure-plan validation is part of the attach/detach timing.
Reopened output must
be parsed through the public source-backed reader and must assert the expected
SVG presence, raster fallback, relationship target, package member closure,
and source preservation for unrelated members.

Inputs are synthetic, bounded, and generated by the harness. They must be
described by byte sizes and hashes, with no native Office or real-user data
claim. The harness may create ordinary files only beneath its own temporary
directory and must remove those files and its isolated Cargo target after the
run. Caller-owned payloads are borrowed where the public API permits; the
report must identify any replacement buffers supplied by the harness as fixture
inputs outside the library's allocation boundary. Each raw lane receipt carries
the FNV-1a-64 hash of its complete synthetic package input and verification
requires that hash to match across fresh processes.

The runner must capture the exact source manifest before and after build/run,
source hashes, Cargo/rustc versions, build flags, command lines, fixture hashes,
raw per-process JSON and timing receipts, and a verifier that recomputes every
summary row from those raw receipts. The runner must refuse bootstrap,
`RUSTFLAGS`, and other lint/test suppression variables. No lane may be presented
as a speedup or regression claim without a named baseline and matched workload.
A newly created isolated Cargo target is removed by the runner on exit; retained
receipts and reports are the only persistent profile artifacts.

The namespace-heavy lane is an absolute resolver-cost observation. It keeps the
inherited declarations and descendant markup below the public reader limits,
while deliberately resolving an early prefix through the scoped namespace
prefix index. The profile records that workload without claiming linear
namespace lookup. The refusal lane records the exact `active namespace bindings` limit
outcome; an earlier package or XML admission refusal is an unexpected result
and fails verification.
